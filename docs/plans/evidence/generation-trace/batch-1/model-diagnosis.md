# 模型重复调用与请求传输诊断

## 本轮结果

2026-09-25，执行 Agent 使用顾声慢日常排练邀约，在同一开场、同一人设和同一参数下重复调用。每个模型的三次系统请求内容完全相同，直连使用该模型第一条系统调用保存的请求。两组分别固定自己的模型标识；DeepSeek 请求另含供应商限制。结构化结果见 [model-diagnosis.json](model-diagnosis.json)。

| 模型                                  | 系统调用                           | 相同请求直连                      | 原始响应重放                     |
| ------------------------------------- | ---------------------------------- | --------------------------------- | -------------------------------- |
| nex-agi/nex-n2.5-pro:free             | 3/3 返回带完整 gametext 标签的正文 | 2/3 返回正文；1 次超时            | 3/3 通过下述三项比较 |
| deepseek/deepseek-v4.1-flash，dekallm | 3/3 返回带完整 gametext 标签的正文 | 3/3 返回正文；其中 1 次缺闭合标签 | 3/3 通过下述三项比较 |

三项比较分别为：重放请求与原请求相同，重放记录正文与原记录正文相同，重放公开正文与原公开正文相同。

重放使用已保存的供应商 SSE 响应，经过正式生成与正文处理路径，过程中没有发送模型网络请求。直连绕过应用的提示词组装和正文处理，但发送的是应用已经组装的请求，因此仍受该请求内容影响。

执行 Agent 撤回此前根据单次失败排除 Nex Pro 的判断。当前样本证明两条通道能够生成正文；这些样本数量不足以证明长期可靠性。

## 已确认的实现缺陷

`packages/core/src/llm/recording-fetch.ts` 将带正文的标准 `Request` 传入 `new Request(input, init)` 后，又把原始 `input` 交给网络层。第一次构造已转移正文，第二次使用会触发请求体已使用错误，网络请求无法发出。

修复后，包装器发送已经合并 `RequestInit` 的 `request`，并附加组合取消信号。请求记录仍在发送前保存。回归测试覆盖标准 Request 正文、init 正文及 headers 覆盖、取消传播和保存内容与发送内容一致。

本轮供应商限制适配器传入标准 Request，暴露了此缺陷。修复前的三次系统尝试均在网络发送前失败，未计入上表的生成样本。此前字符串 URL 调用的正文缺失和重复需要按下一章的原始响应证据归因。

红阶段复现请求体已使用错误；修复后 recording-fetch 与 model-calls 集成测试合计 16 项通过。core 构建、类型检查和两份改动文件的 ESLint 检查通过。独立代码审阅未发现阻断问题。

## 原始响应与语义判断

执行 Agent 对此前顾声慢正式和试聊的六条供应商 SSE 逐条累计 `delta.content`，结果均与保存的模型正文完全相同。正式第二轮的原始响应已经缺少 gametext；试聊第二、三轮原始响应的 gametext 部分完全相同，公开正文也相同。因此，这两项现象已经出现在应用正文处理之前。

上述证据排除了这六条样本中“记录器丢失正文”和“正文处理制造重复”的解释。它仍不能单独区分模型随机性、供应商行为和输入预设对生成的影响。

执行 Agent 阅读了本轮所有成功的系统和直连样本。Nex Pro 能回应用户的次日四点邀约，但个别样本出现活动室与音乐教室混用、正文残留注释结束符、背景指令与楼梯口叙述不一致。DeepSeek 的六条样本均把用户发起的邀约改写为顾声慢发起；第三条直连还把开场已经命名的曲子写成未命名。这些现象在原始模型正文中已存在。公开正文重放一致性通过。下章补充人称与输入核对；邀约主体变化暂作为待验证观察，不作为模型语义不合格的独立依据。

DeepSeek 第二条直连返回 `finish_reason: stop`，但缺少 gametext 闭合标签。执行 Agent 将其记为输出格式缺陷。HTTP 200 和正常停止标志仅证明传输结束，不能代替格式及语义验收。

本轮实际请求包含原样的最新用户消息。执行 Agent 同时发现请求中“最新互动”标签的包围范围与消息边界存在疑点，尚未完成源预设与迁入组装的逐项对照，因此没有把邀约主体偏差归因为模型本身，也没有修改预设。

`qwen/qwen3.8-27b:free` 仍列于模型目录，价格为零；本轮探测返回共享通道 HTTP 429，尚无成功生成样本可用于质量判断。

## 演绎主体与测试输入复核

用户指出测试句必须结合演绎主体、预设人称与消息组装方式判断。执行 Agent 据此撤回将旧测试直接用于判定“邀约主体写反”的结论，保留原始样本和观察。

本轮会话 `wDX5CgiuueXXLyqrSS8OF` 的 `user_snapshot_json` 为 `{"name":"裴修远","description":""}`。实际模型请求包含“裴修远是User的名字，默认扮演此角色”的预设展开结果。`fixtures/role-apps/bindings.json` 另有名为“你”的验收人设，本轮重复调用选择的是裴修远。

源预设 `fixtures/role-apps/presets/tianqin-beta-3.9.json` 启用了“剧情全程严格采用第三人称创作”的人称规则。该规则已经出现在实际请求中。预设的 `names_behavior` 为 0；`apps/api/src/services/prompt-assembler.ts` 将其解析为 off，`packages/adapters-sillytavern/src/compat-assembler.ts` 原样传递用户消息。因此本轮没有在用户消息前自动添加“裴修远：”，也没有形成“裴修远：我……”的重复前缀。

演绎主体的姓名确定用户控制谁；预设人称确定叙述如何称呼人物；台词中的人称由说话者决定。第三人称叙述仍可包含“我叫裴修远”这样的直接引语。模型收到姓名设定，也不代表故事中的顾声慢已经知道这个名字：本轮开场正在询问姓名。

本轮输入“我向顾声慢确认……请继续这段日常对话”混用了角色动作和给写作者的指令，并跳过开场的姓名询问。执行 Agent 尚未用符合本轮开场及人称约定的输入完成重复对照，因此不能据此判断模型本身不理解邀约主体。

针对本轮绑定，下一次测试可直接发送裴修远的台词：`“我叫裴修远。明天下午四点在学校音乐教室讨论社团排练安排，可以吗？”` 消息发送者由已绑定的人设确定，直接引语中的“我”指向裴修远；模型叙述继续遵守第三人称预设。此句尚未执行模型调用。

## 供应商与费用

用户授权的付费调用仅限使用 `deepseek/deepseek-v4.1-flash`，供应商限定 `dekallm`，总额度为 3 美元。本轮诊断适配器设置 `provider.only: ["dekallm"]`、`allow_fallbacks: false`，并将输入与输出报价上限分别固定为每百万 token 0.04 与 0.49 美元。供应商选择字段依据 [OpenRouter 官方文档](https://openrouter.ai/docs/guides/routing/provider-selection)，实际报价来自该模型的端点目录快照。

付费请求共 9 次，其中 1 次 HTTP 429、8 次 HTTP 200。成功响应均报告供应商 DekaLLM。两次成功调用发生在修复前的直连对照，六次成功调用属于上表修复后的系统与直连矩阵。

成功响应报告的费用合计为 **0.0042934617 美元**。逐请求账本保守预留总额为 **0.10437336 美元**；失败请求也保留预留额。HTTP 429 没有报告费用，费用合计只覆盖响应中已报告的值。账本按完整 JSON 的 UTF-8 字节数加 4096 估算输入 token 上界，结合最大输出 token 与报价上限，再乘二预留；每次请求发送前检查累计预留不超过 3 美元。

费用账本保存在工作树 `.tmp/paid-budget.json`，公开摘要见结构化证据。原始请求、响应和诊断数据库保存在 `.tmp/model-diagnosis/` 与 `.tmp/paid-diagnosis/`；鉴权文件单独保存。生产模型绑定保持原值；本轮供应商与费用限制只在诊断适配器中执行。
