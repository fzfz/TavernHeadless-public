# 用户 Web 的系统布局与角色显示布局

## 必须要实现的目标

前端实施者将用户 Web 划分为系统界面与角色演绎内容区。角色作者定义内容区的显示模板和资源，系统提供聊天控件与执行逻辑。管理员试聊与正式用户会话采用同一实现。本方案细化[显示架构](role-status-rendering.md)，其模块边界和验收结果以本文件为准。

“角色卡自带布局”指角色交付包中的版本化显示资源及绑定关系。原始角色卡、提示词、世界书、正则和显示资源仍是分别管理的对象，角色应用的发布记录将它们绑定在一起。角色包导入后的布局由管理端预览、编辑和发布；正式用户会话读取固定的发布版本。

## 布局契约与组件组合

当前角色作者使用[附加模板规范 v1](../character-authoring/template-api.md)和[交互 API v1](../character-authoring/interaction-api.md)。契约字段位于 `snapshot.extensions.tavern_headless.card_view`，唯一结构定义为 `apps/web/prototypes/shared/card-contract.schema.json`。后端角色版本接口原样保存该包，隔离运行服务与浏览器读取同一校验实现。

作者通过通用节点树、CSS、变量绑定和条件组合界面。系统提供唯一消息历史与输入组件、变量绑定、条件计算、列表重复以及声明式动作。布局方案中先前的 `layout=stage/inline/novel` 枚举、固定 `shell/scene` 插槽和限于书店的变量键，只用于旧静态验证。当前后端角色卡原型通过通用节点解释器渲染，作者无需提交这些旧字段。

系统将角色节点树挂载到 Shadow DOM；history 和 composer 插槽投影已有聊天组件。头像来源为包内 avatar 资源与会话演绎者身份。控件数据、条件及每轮更新以作者规范为准。正式发布流程仍须交付完整样式、媒体及模板可用性校验。

## 数据时序与渲染顺序

后端生成流程负责世界书、提示词、LLM、工具、校验以及变量提交。前端得到提交结果后，按消息身份关联显示快照。正式实现的顺序为：

1. 会话创建时固定角色发布版本、显示模板版本和演绎者身份，产生初始显示记录。
2. 用户输入或当前选项触发同一个生成请求；模型生成正文，工具暂存变量变化。
3. 后端完成校验，并在同一次提交中保存回复、接受的变量与显示快照。
4. 用户 Web 对正文执行显示正则并渲染消息；角色渲染器用同一提交结果中的字段绑定状态栏及媒体。
5. 系统当前操作区读取最新有效选项及操作能力。历史回看按下一段规则执行。

角色展示区回看历史时，当前聊天消息、输入草稿、整体页面编排和剧情选项保持当前会话状态。消息内状态卡始终绑定自己的回复；角色头像和演绎者头像分别来自该消息关联的身份。角色显示配置的新版本应用于新会话，管理员已获准调整现有试聊时从后续轮次开始记录新配置。

静态原型从已有 `/variables/resolve` 响应的 `data.resolved` 派生轮次显示记录；`floor.debug.variables` 是原型内部转换结果。正式后端当前还没有本方案要求的不可覆盖历史显示快照接口，因此正式实施需要新增提交记录及读取契约。历史消息从其对应的已提交显示快照读取状态。

## 管理端编辑边界

管理 Web 的角色显示编辑器维护复杂且经常调整的显示配置：页面编排、资源绑定、状态卡 HTML/CSS、变量字段、进度条、选项和聊天主题。角色姓名由角色资源提供；演绎者身份由会话绑定选择。部署资源域名、存储路径等低频运行环境配置由系统配置文件维护。

本次原型已提供页面编排、资源、主题和选项的结构化编辑入口，以及状态卡编辑预览。整屏编排的实际效果通过保存配置后进入同一用户 Web 试聊验证。正式管理端还需提供媒体选择器、选项表单、共享 schema 校验和完整整屏预览；这些属于后续实现工作。

### 本次已运行的 mock 验证

三个显示配置共用同一角色和同一组后端 HTTP fixture，目的是单独验证外观和动作配置的变化。业务对话中的地点仍由变量提供，背景图片不会反向修改该地点。

| 配置       | 布局与资源                                     | 剧情选项                   | 已验证结果                                                             |
| ---------- | ---------------------------------------------- | -------------------------- | ---------------------------------------------------------------------- |
| `bookshop` | 左侧角色展示、右侧系统聊天；书店背景与人物立绘 | 四个发送选项               | 双列布局、历史隔离、消息与输入区各一个、头像加载、手机布局             |
| `harbor`   | 左侧系统聊天、右侧角色展示；港湾背景与独立主题 | 一个填入选项、一个发送选项 | 顺序反转、局部样式、选项动作区分、失败重试、发送新增一轮、历史头像固定 |
| `plain`    | 系统消息列表与消息内状态卡；无背景、无全身立绘 | 空列表                     | 三条历史状态卡正常显示、无选项按钮、双方头像仍存在、手机布局           |

三份显示配置和演绎者数据通过 JSON Schema 校验。管理端验证了八种无效配置及 JSON 语法错误，并完成修改页面布局、保存配置、新建试聊的完整操作，新试聊采用修改后的编排；将选项动作改成 `set_variable` 后校验失败。删除 `chat` 插槽后布局校验返回具体缺失项。港湾模板包含 `.topbar{display:none!important}` 作为样式边界验证输入，系统顶部导航仍显示。页面中有一个 `#messages`、一个 `#composer`，代码将原聊天组件挂入插槽。

验证脚本是 `apps/web/prototypes/checks/layout-boundary.mjs`。运行方式为：`node apps/web/prototypes/checks/layout-boundary.mjs <已安装的Chromium可执行文件> <已安装的Ajv模块入口>`。本次使用本机已安装的 Chromium 和 Ajv 8.17.1，没有安装依赖。脚本创建临时浏览器目录，完成后关闭浏览器并清理目录。

机器结果见 [report.json](evidence/layout-boundary/report.json)。视觉结果见 [书店桌面](evidence/layout-boundary/bookshop-desktop.png)、[港湾桌面](evidence/layout-boundary/harbor-desktop.png)、[港湾手机](evidence/layout-boundary/harbor-mobile.png)、[消息内布局](evidence/layout-boundary/plain-desktop.png)。检查包含 1247 × 884 桌面和 390 × 844 手机视口、默认展开、历史回看、保留输入、生成中限制操作、失败重试、填入和发送。

在用户端原型 URL 上设置 `presentation=bookshop`、`presentation=harbor` 或 `presentation=plain` 可打开对应配置。该参数属于验证入口，产品界面没有新增布局切换按钮。

### 正式后端验收及启动条件

本次问题是布局、资源、身份与动作职责能否分离。上述静态页面已实际执行模板组合和同一聊天控制器，已覆盖插槽布局、样式边界和选项动作；此前的布局检查使用静态 fixture。新增角色卡切换验证使用真实角色卡接口与独立内存 SQLite，范围见下一节；聊天生成仍采用内存模拟。

后端及前端实施者完成以下交付时，验收 Agent 必须启动独立数据库、独立端口的隔离系统，并使用真实后端：

| 实施产物                 | 真实后端验收动作                                 | 完成条件                                         |
| ------------------------ | ------------------------------------------------ | ------------------------------------------------ |
| 显示资源发布与媒体服务   | 发布两套模板及图片，建立新旧会话，重新加载页面   | 各会话保持各自版本；图片引用可读取               |
| 显示快照提交与历史读取   | 实际生成两轮、修改变量、重试与建分支，再读取历史 | 回复、变量与快照的提交身份一致；旧消息仍显示旧值 |
| 当前动作权限与服务端解析 | 对当前选项、过期选项、生成中选项分别提交请求     | 后端依据当前权限处理；动作参数来自服务端记录     |
| 角色与演绎者身份版本     | 更换演绎者或角色配置后继续对话并读取旧消息       | 新消息采用新身份，旧消息保持已记录头像和名称     |

上述接口尚未实现的字段先由共享 schema 与 OpenAPI 定义，再进行真实联调。静态检查与这些真实后端验收分别记录，真实接口完成后才标记对应实施项完成。

## 前一轮后端角色卡驱动验证记录

后端 `apps/api/src/routes/characters.ts` 的版本 snapshot 允许扩展字段。本原型将显示契约放入 `snapshot.extensions.tavern_headless.presentation`，通过现有 `POST /characters/:id/versions` 保存，并通过 `GET /characters/:id` 的 `data.latest_version.snapshot` 读取。该字段路径是拟议契约；现有后端负责原样存取，正式实施者须补充发布时的共享 schema 校验。

用户 Web 的 `character-source.prototype.js` 从 `GET /characters` 建立角色选择列表。隔离服务读取 `characters.seed.prototype.json` 中的角色卡并经版本接口写入数据库；浏览器不读取该种子文件。选择角色后，前端读取其最新版本、验证显示配置，并绑定到独立试聊。前端按 `layout` 与插槽契约组合控件；角色 ID 只用于资源请求和会话身份。后端配置决定模板 HTML/CSS、媒体、显示字段、选项与动作。正式用户入口改为读取已发布版本，管理员入口读取指定草稿版本。

视觉小说的 `novel` 配置定义自动阅读间隔、音乐资源与画廊资源。`novel-view.prototype.js` 将开场白与当前分支已提交回复的显示正文按空行分段，保留消息 ID、段落索引和轮次 ID。前端阅读进度记录当前位置、正文显隐及面板开关。上一段、下一段、自动阅读和跳至最新只移动已有正文的阅读位置。输入框与选项遵循“逐项边界”中的控件执行职责。切换角色时系统停止自动阅读与音乐，保留原会话的输入及阅读位置。

背景与立绘读取当前阅读段落所关联轮次的显示配置；开场白读取会话初始配置。状态面板读取同一记录的变量。当前行动选项遵循“数据时序与渲染顺序”中的历史回看规则。现阶段只验证轮次级媒体配置；段落级场景指令和动态 CG 解锁仍需后端结构化事件契约。

验证入口：`http://127.0.0.1:43871/prototype/apps/user-web/prototypes/user-roleplay.prototype.html?source=backend&session=session-port-bookshop`。检查脚本为 `apps/web/prototypes/checks/backend-character.mjs`；服务脚本为 `serve-character-prototype.mjs`，使用当前 API 源码及独立内存数据库。服务退出后数据库清空。脚本第四参数可指定本机已安装的 better-sqlite3 12.8.0 目录，以配合其已有 Node 25 原生模块；该参数只控制隔离验证进程的依赖解析。

本轮验收检查角色目录、两种布局、正文阅读、会话隔离，以及通过真实版本接口修改模板正文区高度、显示标题和 `fill` 动作后重新选择角色的结果。结果记录在 [角色接口验证报告](evidence/backend-character/report.json)，截图保存在同目录。该检查验证角色存取与前端渲染连接；LLM、正式会话存储、发布权限和历史显示快照仍按上表单独验收。

## 非本次目标

本次完成职责边界方案、可执行原型与 mock 验证。正式媒体服务、版本发布接口、历史显示快照持久化、动态模型选项、条件立绘及生产级模板发布校验留在正式实施步骤。任意角色脚本、SillyTavern 插件运行环境和完整拖拽编辑器作为独立需求评估。
