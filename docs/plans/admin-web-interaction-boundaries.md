# 管理 Web 的编辑边界与后端操作设计

## 必须要实现的目标

设计 Agent 必须以“管理员准备并维护可演绎角色”为目标，对管理端的每项操作明确后端对象、写入时机、实际结果、后续使用方式和结束方式，再修改界面。实施 Agent 必须把这些要求与两端方案中的纵向步骤一起交付。

本文件给出设计建议和源码核对结果。分析基线为 `f0d12bf` 的业务代码及首次编辑边界修订前的原型；本轮没有执行真实后端请求。管理端继续基于 `apps/web` 改进，独立用户 Web 承担实际演绎。

## 设计依据

### 界面与配置文件的划分

设计 Agent 必须结合字段用途、编辑复杂度和调整频率划分编辑入口。

| 条件                                            | 适合的入口             | 原因                                                                 |
| ----------------------------------------------- | ---------------------- | -------------------------------------------------------------------- |
| 结构复杂，存在条目顺序、关联 ID、启停或版本关系 | 结构化编辑器           | 管理员能够直接操作业务对象，减少手工维护关联的负担                   |
| 字段简单，但会按角色反复调整并通过试聊判断效果  | 表单和选择器           | 管理员能够在配置、试聊和结果之间连续操作                             |
| 低频部署参数，通常由维护者设置并随进程启动生效  | 配置文件               | 字段可直接阅读，界面不会增加明显便利                                 |
| 编程逻辑、算法、外部程序实现                    | 源码文件与现有开发工具 | 管理端管理其注册信息、启用状态和运行结果；代码开发使用适合代码的工具 |
| 外部格式的未知扩展字段                          | 导入导出与高级原文编辑 | 主编辑器保留未修改字段，专用表单覆盖已有明确 schema 的部分           |

预设、世界书、正则等在当前后端保存为数据库资源。JSON 是其交换或存储表示。管理员手工修改导出文件后，必须通过导入或资源更新 API 提交；编辑磁盘文件本身不等于修改数据库中的资源。低频配置文件的判断不能直接套用到这些资源。

### 操作名称与写入时机

本表统一定义后文引用的操作含义。

| 操作             | 管理员改变的对象                       | 写入与界面结果                                                                           |
| ---------------- | -------------------------------------- | ---------------------------------------------------------------------------------------- |
| 新建资源         | 一份新的预设、世界书、角色或其他资源   | 打开表单只产生编辑草稿；管理员提交后由后端返回新资源 ID，再加入资源列表                  |
| 新增条目         | 当前资源中的一条内容                   | 在整份资源编辑器内先修改编辑草稿，点击保存后提交完整文档；保存结果返回该资源的新版本     |
| 编辑资源         | 已存在资源的内容                       | 加载详情及版本，提交修改；服务端成功后显示新内容和版本，冲突时保留输入并提供重新读取操作 |
| 复制资源         | 原资源的独立副本                       | 复制表单以原内容初始化，提交后获得新 ID；修改副本保持原资源不变                          |
| 绑定资源         | 某角色应用或会话指向哪份资源、哪个版本 | 选择器改变绑定草稿，保存绑定后生效；此操作保持资源本体内容不变                           |
| 保存角色应用草稿 | 准备下一次试聊或发布的组合配置         | 后端保存草稿及修订号；成功后才能把该修订作为试聊依据                                     |
| 发布             | 将一个完整配置修订提供给新用户会话     | 后端创建发布记录并更新发布入口，具体版本规则引用两端方案                                 |
| 移除绑定         | 角色应用或会话与资源的关联             | 仅解除对应关联；必填资源解除后，配置校验返回缺项                                         |
| 删除资源或会话   | 后端实际资源                           | 后端确认删除成功后移出列表；操作失败时保持对象可见，并展示具体原因和处理入口             |

编辑器应采用统一的保存方式。当前 Web 的预设编辑器使用整份文档保存，条目增删与排序继续作为未保存编辑；后端的条目级接口保留供其他调用方使用。界面必须清楚区分“条目已加入编辑草稿”和“预设已保存”。

## 试聊应如何设计

### 使用目的与默认行为

试聊用于判断某份配置在连续上下文中的效果，属于可保存、继续和删除的管理员会话。管理端负责入口、配置和记录维护，实际聊天跳转用户 Web；聊天实现与正式演绎共用，交接契约以[主计划](role-app-dual-web-plan.md)为准。管理员打开角色应用时，界面加载已经存在的试聊，显示“继续试聊”；没有试聊时显示空态和“开始试聊”。打开页面或反复点击导航只改变当前选择。

“开始试聊”提交一次创建请求。创建期间按钮显示进行中，收到后端 session ID 后才把会话加入列表。失败时保持空态并保留输入。再次进入同一试聊继续原会话；管理员明确选择“新建独立试聊”时才创建另一条，用于比较配置或排除旧上下文影响。

每条列表记录显示名称、所用配置修订和状态，并提供继续、重命名、归档/恢复、删除。当前阶段可以将归档入口放在菜单中，但创建与删除必须在同一交付步骤完成。

### 保存配置与试聊的关系

管理员修改配置后先保存角色应用草稿。现有试聊继续使用其创建时的配置，并显示“此试聊使用修订 X；当前草稿为修订 Y”。管理员可以继续分析旧试聊，也可以明确创建使用 Y 的独立试聊。原型中的“应用到新试聊”应拆成“保存草稿”与“用此修订新建试聊”，避免一次点击同时承担含糊的保存和创建。

试聊标题、草稿修订和测试用途必须由后端统一定义并保存。现有 session 支持资源版本和模型配置，但现有列表筛选没有角色应用/试聊用途字段。两端方案中的 preview-sessions 适配必须在后端保存并查询该关系，前端按接口结果更新列表。

### 发送、失败和删除

用户 Web 的统一发送操作必须指向真实 session，复用已有 respond/stream 服务。用户输入、楼层状态、结果和失败原因由后端结果驱动。列表中的“已创建”与聊天区域的“已生成”是两个不同结果；创建成功本身不代表模型生成过回复。

删除普通试聊调用 `DELETE /sessions/:id`。界面说明会删除该试聊及其对话记录；管理员提交后，以后端删除结果更新列表。生成中返回的 `active_run_in_progress` 应显示为“此试聊仍在生成，完成后可以删除”。若后续提供取消生成入口，必须接入真正取消运行的服务，界面必须以服务端运行终态确认取消结果。

管理员需要保留测试记录时使用归档，恢复时将状态改回 active。退出试聊页面只关闭视图。临时对话的 discard/finalize/cancel 使用独立状态含义，其正文清理取决于维护配置，界面必须分别显示状态终结结果与正文清理结果。

### 试聊最小验收

| 操作               | 后端证据                          | 页面完成条件                                     |
| ------------------ | --------------------------------- | ------------------------------------------------ |
| 打开角色、继续试聊 | 查询已有 session                  | session 总数不变，显示原历史                     |
| 首次开始、明确新建 | 一次成功创建及唯一 ID             | 创建成功后出现一条记录；重复点击不会意外创建多条 |
| 发送消息           | 同一 session 的生成楼层和真实结果 | 页面展示实际结果；失败保留可处理状态             |
| 修改并保存草稿     | 新草稿修订及原试聊绑定            | 原试聊版本不变，新建试聊明确使用新修订           |
| 重命名、归档、恢复 | PATCH 返回结果                    | 列表与刷新后内容一致                             |
| 删除生成中的试聊   | active run 与 409                 | 记录保留，界面解释暂不能删除                     |
| 删除已结束的试聊   | 删除成功、后续查询结果            | 记录从列表移除，删除最后一条后显示空态           |

| 记忆               | 检索、详情、统计、任务状态；需要维护时提供修改、删除、重建、压缩、取消和重试                  | 维护周期、worker 参数和默认保留策略属于部署配置；每次具体维护作业属于界面操作                                                            | 保留观察，维护独立页         |
| 提示词运行解释     | 模式、生效资源、组装结果、命中条目、差异和历史 explain；受支持的注入编辑                      | UI 只开放后端已支持字段；一般角色作者无需操作底层执行结构                                                                                | 与试聊配套                   |
| 项目与工作区       | 当前归属和已有对象选择；需要维护时提供基础信息页面                                            | 完整成员治理、Agent 编排、节点图编辑独立规划，不塞入角色配置右栏                                                                         | 最小归属先行                 |
| 账号、客户端和权限 | 管理员身份、角色访问范围、客户端凭据状态和后端支持的管理动作                                  | 认证模式、签名根密钥、主加密密钥和启动策略保留部署配置；操作凭据更新遵循现有后端机制                                                     | 与真实用户接入配套           |
| 备份与运行排查     | 后端支持的备份提交、恢复预览、任务结果和失败原因                                              | 备份目录、worker 并发、轮询间隔及文件有效期保留配置文件                                                                                  | 独立运维入口                 |
| 服务部署           | 界面展示已有接口确认的健康状态和功能可用性                                                    | PORT、DATABASE*URL、CORS、ACCOUNT_MODE、全局 ENABLE*\*、维护间隔和 worker 参数由 `.env.example` 及 `apps/api/src/config.ts` 对应配置维护 | 文件为主                     |

一个复杂配置并不意味着每个字段都必须先建专用控件。首批编辑器先覆盖当前 schema 中影响角色配置和试聊的常用字段，并完整保留其他字段；当某个高级字段反复使用、需要关联校验或批量操作时，再增加结构化控件。

## 页面结构与导航

管理端以现有三栏工作区为基础，按下面的用途组织。

- 左侧导航负责角色应用选择、试聊列表、资源库入口，以及现有模型、工具、MCP 管理入口。列表菜单承载对象的重命名、归档和删除。
- 中间区域展示所选试聊的配置和运行记录，继续试聊入口跳转用户 Web。管理员进入资源编辑时，使用较宽的编辑页或弹窗：左边是条目列表，右边是正文与字段，底部是保存和取消。大型预设及世界书编辑必须采用上述宽编辑区域。
- 右侧检查器负责当前角色应用或会话的绑定摘要、生效来源、校验状态、历史解释和发布信息。资源选择器旁提供“编辑资源”入口，进入同一个资源编辑器。
- 编辑器保存后返回原角色应用位置。保存已有资源与更新角色应用引用分别显示结果；管理员明确选择新版本后，再保存角色应用草稿。界面显示该资源当前是否被其他对象引用，以后端引用查询结果为准。

资源库页面的常规操作为新建、导入、复制、编辑、导出、版本和删除。新建与导入进入同一资源管理体系，资源选择弹窗专门负责选取与绑定。按钮名称必须准确对应实际打开的编辑器或选择器。

## 原型修订与正式实施的对应关系

第一步设计 Agent 根据下表修订页面结构、操作含义和状态展示，并使用示例数据演示操作；真实请求、持久化及运行结果由实施 Agent 在第二至第六步交付。表中涉及真实接口的修正属于正式实施要求。

| 首次修订前的问题                                        | 对应修正                                                                         |
| ------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 页面启动时执行 `newTrial()`，点击“＋试聊”就追加内存记录 | 按试聊一节设计加载/继续/明确新建流程；创建与删除一起验收                         |
| “应用到新试聊”同时承担配置与新建                        | 按统一操作表拆分保存、选择修订和创建                                             |
| 预设只有两个名称可选                                    | 恢复现有完整编辑器，并补齐新建整份与复制入口                                     |
| 资源选择弹窗显示为“管理”，实际上只有绑定按钮            | 把选择和管理分开，管理页提供资源完整操作                                         |
| “沉稳/热情”是没有对应持久化字段的本地下拉               | 通过角色性格正文或预设内容编辑；明确保存到哪个资源                               |

## 验收清单

设计 Agent 必须为每个写入按钮填写一条操作记录：操作对象、后端 method/path、输入来源、保存时机、成功标识、列表或详情刷新方式、失败后的处理方式，以及该对象的退出/删除/归档方式。尚无后端能力时，记录明确标为“需补后端”，并与接口实现安排在同一纵向步骤。

- 试聊创建、继续、发送、改名、归档恢复和删除满足本文件的试聊最小验收表。
- 预设同时具有“创建整份资源”和“新增条目”，二者写入时机与版本结果可辨。
- 管理员可以从界面完成复杂资源编辑，并能取消未保存修改；保存冲突时输入仍在。
- 绑定资源、编辑资源和发布配置的结果分别核对，避免把显示名称变化当成后台配置生效。
- 资源版本引用、删除限制和错误提示均来自真实接口结果；缺失的引用检查列入发布功能后端工作。
- 部署配置保留明确的文件入口与生效方式；相同运行参数的最终值和来源可由既有运行时接口解释。
- 独立语义审阅 Agent 阅读本文件及两端方案的修改，主 Agent 核对并处理意见。

## 非本次目标

本轮交付编辑边界、完整操作设计和两端实施顺序修订。业务代码接入、真实服务运行、用户数据写入及新版原型实现属于后续实施。

本次不以“覆盖全部 API”为页面建设目标，也不建设通用文件管理器、源码 IDE 或所有基础设施参数的 Web 配置台。
