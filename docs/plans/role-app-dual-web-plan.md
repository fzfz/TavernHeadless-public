# 管理 Web 端、用户 Web 端与后端开发计划

本计划中的“执行 Agent”负责开发、测试和验收取证；用户端系统、管理端系统及后端系统执行各自的程序运行行为。工作项按目标文件和模块划分。

## 首要职责边界：后端、角色卡与 Runtime

本节定义本计划的正文交付与页面渲染职责。执行 Agent 必须按本节修正原型及后续步骤；下文引用的显示方案和旧验收记录中，涉及正则职责的表述必须按本节同步更新。

| 负责模块                       | 必须承担的职责                                                                                                                                                          | 交付对象                                                                                        |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 后端 `apps/api`                | 按会话绑定的发布版本加载角色、预设、世界书、正则、人设和模型配置；执行提示词组装及预设输出处理，区分原始响应、角色正文和 Agent 结构化更新；保存执行记录与楼层变量快照。 | 向用户 Web 提供正文文本流、完成结果、变量提交事件和可读取的历史快照；原始响应保留在生成记录中。 |
| 角色卡附带的模板与脚本         | 定义角色自己的布局和表现格式，解析角色正文，通过 Runtime API 更新界面。例如顾声慢脚本解析 `[bg]`、`[show]`、`[choice]`，据此选择背景、立绘和选项。                      | 角色模板、脚本、资源映射、事件回调及对 Runtime API 的调用。                                     |
| 用户 Web 的 Runtime 与渲染引擎 | 提供布局注册、元素更新、文本流回调、楼层变量读取及更新回调、图片、立绘、选项和媒体能力；执行角色脚本的调用，管理监听器、计时器、媒体及历史轮次资源的释放。              | 根据角色配置实际渲染的页面；系统通用实现通过公开 API 服务各角色，角色专有标签由角色脚本解释。   |

执行 Agent 必须按原规则的用途处理正则：

- 旧 HTML 美化、背景替换、状态栏占位符规则迁移为角色模板和脚本，由 Runtime 渲染，随后从迁移后的执行配置移除旧规则。
- 预设输出标记清理由后端按绑定的预设配置执行。后端必须明确流式阶段与完成阶段的正文提取规则，向 Runtime 交付角色正文。
- 提示词历史裁剪等规则继续由后端提示词组装模块执行，并保留来源、顺序和执行记录。
- 纯显示文本替换仅在角色明确需要时作为可选能力配置。Runtime 的基本渲染流程直接使用角色正文、模板、脚本和变量快照，显示正则属于可选处理步骤。

执行 Agent 必须修正 `apps/web/prototypes/shared/formal-transport.prototype.js` 中整套显示正则的统一前置处理；执行 Agent 必须先接通上述预设输出处理，再由前端交付正文给角色脚本。执行 Agent 必须验证顾声慢的背景、立绘表情、对白分页、行动选项和状态栏由角色脚本调用 Runtime API 实现，并核对文本流、完成结果与历史重载使用同一正文契约。此前“接通显示正则后正文恢复”的验收记录只证明当时页面恢复显示；本项职责调整完成后必须重新验收。

当前职责重做的实现、接口与验收记录见[正文交付与角色渲染职责实施](preset-output-responsibilities.md)。

## 必须要实现的目标

1. 用户 Web 的产品行为采用[用户 Web 需求规格](../ixd/user-web/user-web-requirements.md)；执行 Agent 按其第 5 节核对接口接入，并按第 6 节验收。

执行 Agent 必须同步建设角色应用管理端、简单用户 Web 和后端发布调用能力，使管理员能够配置角色的完整运行环境，用户能够直接进入演绎。

本方案中的角色应用、发布配置和生成执行术语统一采用[生成执行领域](../../packages/core/CONTEXT.md)的定义。

本方案将“纵向验收”定义为：执行 Agent 从管理端执行操作，在后端确认保存或执行结果，再从独立用户端观察对应效果。每一步均交付可操作界面和可追踪结果。第一步使用页面原型与隔离后端验证契约，其余步骤使用正式 API、数据库与指定测试模型；自动化测试可以使用确定性模型桩。

最小成品必须支持以下流程：管理员配置并试聊角色 → 发布角色应用 → 用户选择角色并开始对话 → 后端按发布配置演绎 → 管理员更新版本并排查运行问题。用户端的正常页面展示角色、对话、角色配置产生的状态栏和明确开放的用户选项。

管理端各编辑页的字段覆盖、演绎槽位、导演与 Agent 配置以[逐页核对](admin-editor-page-audit.md)为准。

管理端的编辑入口、资源操作含义和试聊生命周期以[管理 Web 的编辑边界与后端操作设计](admin-web-interaction-boundaries.md)为准。各步骤必须同步完成创建对象后的继续使用、删除或归档入口。

轮次调试与历史记录要求见[管理端轮次调试与后端记录](admin-round-debugging.md)。第三步交付[角色状态栏与前端渲染架构](role-status-rendering.md)规定的显示模板、提交快照、剧情选项、统一聊天显示流程和管理端执行对照，第四步补齐完整运行排查。

执行 Agent 必须将每一步组织为可独立验收的批次，每批均由管理 Web、用户 Web 与后端联合验收：当前批次在已验收版本上提供两端正式页面入口、完整操作流程、可见结果及对应的后端记录，执行 Agent 在后续批次尚未实现时仍能复现该流程。执行 Agent 必须以相同会话、轮次和执行标识核对两端结果，保存两端截图或录像、接口响应及明确结论；当前批次验收通过后，执行 Agent 再细化下一批。生成过程追溯按[正式分批实施计划](generation-trace-foundation.md)交付，其中首批合并完成本计划第二步所需的最小真实闭环；其余正式建设范围继续按本计划执行。

每批的执行 Agent 必须按[每批两端验收标准](generation-trace-foundation.md#每批两端验收标准)，分别提交管理 Web 与用户 Web 的接口、业务逻辑、数据可视化、布局、像素级样式和交互验收结果，并提交联合结论。执行 Agent 必须为当前交付场景登记对应原型基线，按该标准完成逐项检查；批次完成条件为两端各项检查及联合验收全部通过。

## 原型后端接入约束与纠正任务

两端系统必须通过现有正式 API 获取资源、创建和读取会话、发送消息及读取执行记录。后端已有实现的能力必须复用其接口和服务。新增接口只承载现有后端缺少的能力，按现有路由、schema、错误码、账号作用域和测试规范实现，并在本计划登记正式实现任务。

发布版本创建会话、人设与开场选择、正式生成链路分别由下表 C2、C3、C4 定义；宏处理由 C5 定义。

[当前接入核查](prototype-backend-gap-audit.md)记录已经发现的绕过路径。当前 `/script-api` 的会话、生成和提交实现属于待替换对象；它们的成功结果只作为 Runtime 协议的局部证据。执行 Agent 必须先完成以下纠正，再继续完整角色迁移验收。

| 顺序 | 执行主体、对象和动作                                                                                                                                                                              | 产物与完成条件                                                                                                                                                                                            |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C1   | 执行 Agent 核对正式资源及会话接口，并将原型中的调用改为 `/users`、角色/预设/世界书/正则接口、LLM Profile 与实例接口。                                                                             | 接口对照与真实资源记录；管理端读取和保存后，正式接口返回相同内容。                                                                                                                                        |
| C2   | 执行 Agent 补充角色应用发布记录与按发布版本创建会话接口；后端系统创建会话时读取不可变发布记录，复用现有资源版本和会话绑定服务。当前角色版本接口仅保存单一角色版本，完整角色应用发布属于新增能力。 | 发布记录的 schema、持久化和接口；用户端仅凭发布版本、人设、开场创建会话，发布记录固定角色卡、预设、世界书、正则、Runtime 资源、变量更新配置及模型槽位；后端返回完整固定绑定，发布后编辑资源不改变旧会话。 |
| C3   | 执行 Agent 在用户端接通人设列表及开场选择；后端系统在创建会话时固定人设快照、展开开场并提交初始变量。现有 `/users` 和 `user_id` 绑定直接复用，开场初始化扩展纳入正式会话流程。                    | 两个人设、两个开场交叉验收；页面名称、头像引用、开场、世界书和最终模型请求中的人设一致。                                                                                                                  |
| C4   | 执行 Agent 替换专用 `/send` 和内存提交，使用户端系统调用 `/sessions/:id/respond/stream`，由现有后端完成提示词组装；执行 Agent 将新增角色变量规则接到现有生成和 Agent 提交流程。                   | 正式消息、floor/page、变量快照及 Agent 记录可查；Runtime 文本流、每次提交回调与这些记录一一对应。                                                                                                         |
| C5   | 执行 Agent 复用现有宏引擎，检查预设、世界书、开场、历史、正则与更新 Agent 的处理阶段；用户端系统按首要职责边界接收后端正文，并交给角色脚本调用 Runtime 渲染。                                     | 人设宏、角色宏、变量读写宏及未知宏的证据；读取宏的实际展开值、写入宏的提交结果、失败请求的变量状态均可核对。支持边界见宏核查文档。                                                                        |
| C6   | 执行 Agent 统一管理端试聊跳转和脚本用户端；接入正式历史、编辑、删除、重新生成、分支及生成详情。                                                                                                   | 同一会话贯通两端；各操作是否可用依据后端当前状态；服务重启后读取已保存记录。                                                                                                                              |

执行 Agent 必须为新增发布、开场初始化、Runtime 交付与事件映射、角色变量更新配置的接口在正式实施时补齐持久化、OpenAPI、SDK 与分支测试。执行 Agent 通过调用已有正式接口完成接入纠正。

## 产品与模块边界

### 两个 Web 的用途

| 模块                                                         | 主要页面                                                               | 责任                                                             |
| ------------------------------------------------------------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `apps/web`，现有管理端                                       | 角色应用列表、配置详情、试聊列表与跳转、发布记录、运行详情、资源编辑   | 管理员准备可直接使用的角色，发布配置并维护运行结果               |
| `apps/user-web`，拟新增用户端                                | 可用角色列表、角色介绍、我的对话、统一聊天页面（正式演绎与管理员试聊） | 使用者选择角色、开始或继续对话、处理生成失败；页面适配桌面和手机 |
| `apps/api`                                                   | 管理 API、用户调用 API、发布解析与现有运行服务                         | 保存配置、解析版本、创建会话、执行演绎并检查会话归属             |
| `packages/official-integration-kit/sdk` 与 `packages/shared` | 两端共用的类型、请求方法、错误映射                                     | 前端读取统一接口定义；后端按 schema 校验输入输出                 |

管理端负责试聊入口、配置及运行排查；试聊发送与消息展示迁移到用户 Web 端。资源管理保留为可复用资源的维护入口。现有管理 Web 端已接动作的功能全部保留，逐项按恢复复查清单核对；删除或缩小已有功能前，执行 Agent 必须提交理由与影响并获得用户同意。静态图表和原有未接动作按钮按用户要求暂不恢复。

### 唯一聊天前端与试聊跳转

`apps/user-web` 是唯一聊天前端。试聊和正式演绎使用同一个聊天路由组件、会话状态管理、消息操作、流式处理、失败重试、历史加载、分支切换、变量读取和显示正则流程。后端通过会话用途、归属和权限区分草稿试聊与正式会话；前端按后端能力结果提供可用操作。管理 Web 端保留配置与调试页面，通过跳转进入这套聊天界面。

管理员保存角色配置后点击“开始试聊”，管理接口创建并固定该草稿配置的试聊 session，成功后跳转到用户 Web 的该会话。点击“继续试聊”只打开已有 session。用户 Web 在管理员试聊时显示角色、草稿修订及“返回管理端”“查看生成详情”入口；正式使用者进入同一个聊天页面，读取已发布会话及其获准操作。

执行 Agent 必须定义管理端到用户端的会话交接契约；用户端系统使用后端校验的短期、单次、限定试聊会话的交接凭据兑换会话访问权限；浏览器导航携带会话标识和交接标识，管理 API 密钥留在管理端认证上下文中。后端分别验证创建者、会话用途、读取及操作权限。URL 中的模式或会话 ID 只用于路由，授权由后端验证。正式用户身份与管理员试聊身份分别保存，用户正式历史列表保持原归属；交接失效时提供返回管理端重新打开的入口。该契约必须支持两个 Web 使用独立地址。

管理员从试聊消息打开管理端生成详情时携带会话、分支、楼层、页面及执行标识；返回用户 Web 后恢复原会话和消息位置。往返过程只读取已有记录，流连接重新建立前先查询运行状态；后台仍在执行的生成继续使用同一次运行。配置修改按发布与会话规则生效，返回聊天后重新读取会话配置。

执行 Agent 必须迁移管理端已有的发送、编辑消息、删除消息、重新生成、分支选择及聊天展示到用户 Web 的同一消息操作模块。管理端保留试聊生命周期管理、会话配置调整、变量及记忆维护、工具/MCP、Agent 和运行记录查看；这些入口与用户 Web 中的当前会话或消息关联。迁移必须按功能恢复清单逐项验收，旧聊天实现只在对应功能迁移并验收后退出使用。

正则编辑器与管理端执行记录可以复用同一显示处理模块，展示规则输入、结果及诊断；聊天状态和发送流程统一由用户 Web 维护。管理端的“查看聊天效果”打开对应用户 Web 会话。

### 已确认的页面与操作规则

执行 Agent 必须在现有工作区上完善功能，并以[功能恢复复查](admin-web-restoration-review.md)逐项核对保留情况。右侧“配置”标签同时容纳角色配置和发布操作；“试聊详情”展示会话配置，“生成详情”从具体消息进入并定位其楼层及执行记录。

角色卡、预设、世界书、正则、LLM Profile 和演绎人设的资源下拉框用于改变当前角色配置的资源绑定。选择后立即显示选中资源及可选版本，并标记配置尚未保存；独立的编辑按钮打开该资源编辑器。资源保存形成新版本或配置内容；角色配置保存固定所选引用。编辑当前绑定资源后，界面必须明确标示角色草稿是否选用了新版本，管理员保存角色配置后才能据此试聊或发布。

发布按钮根据当前角色应用、已保存草稿及发布记录计算状态。存在未保存修改时先完成保存；已发布相同配置时显示已发布状态；存在新配置时显示“发布新版本”。发布序号由后端返回。历史版本操作显示“切换到 vN”，确认界面写明新对话将使用哪个版本；停止发布后的操作显示“重新发布 vN”。角色切换后，绑定、草稿状态、发布状态和历史记录必须同步更新。

结构复杂或经常通过试聊调整的资源在界面编辑；低频部署配置沿用配置文件。各资源的字段、创建与删除能力按[逐页核对](admin-editor-page-audit.md)和[编辑边界](admin-web-interaction-boundaries.md)实现。执行 Agent 必须为每个写入动作记录接口、对象、保存时机、成功结果和异常处理。

### 身份与作用域

执行 Agent 必须区分以下三个对象：管理员账号负责维护应用；使用者身份负责拥有用户端会话；现有 `/users` 资源承载演绎中的人设快照。演绎人设名称的修改必须保持会话所属使用者不变。

本方案建议第一版以受邀使用为入口，身份方案仍待用户确认：管理员为测试使用者 A、B 分别签发限定角色应用的一次性进入码，使用者在用户 Web 输入进入码后获得后端用户会话凭据。后台保存进入码到使用者及可用应用范围的对应关系；浏览器刷新后通过有效用户凭据恢复自己的对话。此流程同时作为第一版最小身份机制，用户注册、社交登录与跨设备账号恢复属于后续工作。

用户 Web 的 API 必须从该凭据识别使用者。前端只发送角色应用标识、演绎输入及受支持的交互选项，后端从发布记录选择资源和运行配置。管理端模型凭据留在后端的现有凭据存储中。现有 SDK 的 `accountId` 仅形成账号提示头，后端认证模块必须从真实认证上下文识别管理账号。

### 发布与会话规则

本节统一定义各步骤引用的状态规则。

1. 管理员编辑可变草稿。发布服务校验资源可用性，并生成不可变的发布记录，最后更新角色应用的当前发布指针。
2. 发布记录必须固定角色卡、预设、世界书、正则版本，以及提示词模式、LLM 的各启用槽位、provider、model、实例参数和启用能力设置。版本资源必须在被发布记录或会话引用期间可读取。
3. 模型密钥采用可轮换的凭据引用；模型选择、端点和参数属于发布配置。管理员仅轮换密钥时可以维持原引用，修改模型、端点或参数时必须形成新发布配置。
4. 用户创建会话时，后端固定角色应用发布 ID 和解析后的运行配置。随后生成按该记录执行；项目覆盖或资源草稿修改必须保持该会话原配置。发布和创建会话并发时，每个会话必须绑定到一个完整发布记录。
5. 第一版支持角色卡、LLM、提示词预设、世界书、正则和现有必需运行槽位。第二步两套验收配置的必需资源、变量更新和渲染范围按[首批角色与绑定](generation-trace-batch-1.md#首批角色与绑定)接入；其他配置可以明确停用可选世界书与正则。第三步扩展配置编辑、显示正则及变量读取与渲染，状态栏按[显示方案](role-status-rendering.md)实现，并接通内置变量工具及其暂存、校验、提交路径。其他工具、MCP、记忆和项目 Agent 的完整配置及运行接入归第四步；各步尚未支持的可选能力保持显式关闭，发布校验返回具体缺项。消息内及整屏 HTML/CSS 显示模板、字段绑定和剧情选项按显示方案交付；本版作者 JavaScript 的执行范围按“接口与数据设计”和 R7 交付；第三方状态插件属于后续需求。
6. 停止发布关闭角色应用的新会话入口，已有会话继续按原版本演绎。切换到某个历史发布版本只改变后续新会话的版本。管理员紧急停用全部历史会话属于另一个功能，本次保持现有账号和凭据停用能力。
7. 草稿试聊与正式演绎使用相同的配置解析器和生成服务。试聊会话记录管理员试聊用途，并与用户的“我的对话”列表分开。试聊可以使用完整草稿快照；正式用户会话必须引用发布记录。 管理 Web 端保留对试聊会话绑定、模型和提示词模式的调整，变更用于后续轮次；每个已生成轮次保留当时的记录。已有功能恢复清单见 [管理 Web 端原型恢复复查](admin-web-restoration-review.md)。
8. 发布版本缺失、凭据不可用或生成失败时，后端返回具体错误，前端提供对应的处理操作。演绎结果以真实生成和保存结果为准。

上述规则是本方案的建议默认值。第一步分别确认两端的页面结构与操作入口；发布与用户会话之间的联合状态按第二步起的真实联调验收。

### 第一步：设计并操作两端流程原型

**执行主体与产物：** 设计 Agent 先按编辑边界文档为各写入按钮记录后端对象、接口、保存时机、成功结果及失败处理，再使用 prototype 技能，分别交付 `apps/web/prototypes/admin-workspace.prototype.html` 和 `apps/user-web/prototypes/user-roleplay.prototype.html`。两个文件各自独立打开。管理端原型依据现有 `WorkspaceNav.vue`、`WorkspaceCanvas.vue`、`WorkspaceInspector.vue` 和顶部栏布局设计，保留深色工作区的资源、配置及调试布局，在其中补充角色应用配置、试聊跳转和发布入口；原聊天区域调整为试聊记录及运行详情。用户端原型单独提供角色介绍、我的对话及消息输入。页面文案按实际产品用途编写，验收说明集中在本方案中。原型保存在 `codex/role-app-prototype` 分支，后续正式实现从确认的设计重新编写。

**可视验收路径：** 用户在管理端选择角色应用，通过资源编辑器编辑内容，在右侧检查绑定与生效配置，跳转用户端开始或继续试聊，明确新建另一条试聊后删除该记录，在右侧“配置”标签内发布、停止发布和切换发布版本并查看发布记录，在“试聊详情”查看会话配置。用户另行打开用户端原型，选择角色、开始对话并从历史列表继续对话。两个原型使用同一组符合接口 schema 的场景数据；原型间跳转携带会话与场景标识，以展示对应记录，真实会话交接及持久化由第二步实现。管理端生成详情的 mock 响应按后端接口 schema 构造，页面展示结构由明确转换产生；跨页面发布同步由第二步开始的真实 API 联调验证。设计 Agent 必须同步补齐用户端状态栏、多轮变化、生成中、失败重试和变量读取失败的布局，试聊和正式会话均由用户端原型的同一个聊天页面展示。原有正则状态表格属于已实现原型场景；消息内及整屏模板、逐轮显示数据、模板编辑预览与选项交互已按[显示方案](role-status-rendering.md)补充，当前等待用户验收。系统与角色布局的归属和三配置 mock 验证见[布局边界方案](role-layout-boundary.md)，正式实施按其中真实后端验收表完成。真实生成失败与重试按照第六步验收。

**完成条件：** 设计 Agent 按编辑边界文档修订两个原型并提交用户验收。用户确认管理端是在现有 Web 工作区上的功能改进，用户端具有独立的演绎入口，且两端的页面结构和操作含义清楚。设计 Agent 将用户确认的设计结论记录在本方案中。配置与发布合并为一个标签；生成详情必须展示有数据时的展开布局和可操作状态。原型中的标题及字段标签必须明确对应的对象。开发缺口按本方案“当前进度与交付顺序”的文档归属维护。

### 第二步：完成两套完整角色配置的发布与演绎

**身份入口决策：** 执行 Agent 先提交进入码方案的界面与接口契约供用户确认，再实施对应凭据入口；角色发布与生成服务的独立工作可以先行。以下进入码路径按“身份与作用域”的建议方案描述。

**同步实现：** 执行 Agent 在后端建立角色应用、发布快照、受邀使用者身份与创建会话入口，复用现有资源服务、LLM Profile 和生成服务。两套验收配置的角色全名、世界书、共同预设、正则及其他运行依赖统一由[首批角色与绑定](generation-trace-batch-1.md#首批角色与绑定)定义；执行 Agent 在管理端接通完整绑定检查、发布、试聊交接和按已确认身份方案提供的进入入口。执行 Agent 在用户端建立独立 `apps/user-web`，实现角色介绍、开场选择、角色渲染、开始对话、发送消息、刷新后继续与删除会话。后端必须固定会话资源版本、解析各必需模型槽位，并检查使用者归属；用户端按服务端结果更新列表。本步同时交付草稿试聊创建、继续与会话交接，调用历史和失败传播按[首批实施细则](generation-trace-batch-1.md#首批实施细则)执行。资源删除必须返回具体引用对象，第五步扩展历史版本管理。

**可视验收路径：** 执行 Agent 必须对首批两套配置分别执行以下流程：管理员检查绑定并保存配置 → 点击试聊进入用户 Web，发送消息并从消息跳回管理端查看记录 → 返回同一试聊并核对会话和消息数量 → 发布 v1 → 使用者 A 通过确认后的身份入口进入角色并选择开场 → A 连续演绎并看到对应正文和已提交状态 → 管理员查看同一会话、v1 配置及实际请求响应 → 刷新两端并重启测试服务，读取已结束历史 → A 继续原会话 → A 删除会话，后端查询确认结果。四条联合流程及证据要求统一见[首批专项完成条件](generation-trace-batch-1.md#首批专项完成条件)。

**异常与边界：** 试聊交接凭据失效或已兑换时返回管理端重新打开；越权访问已有试聊被拒绝；本步从管理详情返回试聊的验收使用已结束轮次，核对原会话和消息数量。执行中返回时查询同一次运行并恢复显示的能力按[生成追溯第四批](generation-trace-foundation.md#批次安排与独立可视验收)交付，恢复后用户消息数量保持不变。缺少模型时管理端定位缺项；未发布角色不能开始对话；进入码无效或已经使用时用户端提供重新取得进入码的操作说明；使用者 B 的列表中仅出现自己的会话，且不能读取或删除 A 的会话；生成中的删除返回具体状态并保留记录；创建失败保持可重试空态，重复点击创建只提交一次。

**完成条件与证据：** 执行 Agent 按首批专项清单保存两套配置的两端截图、应用、发布、会话及轮次标识与真实生成结果。用户创建和发送请求按正式契约提交角色入口、开场、人设及演绎输入，后端从固定配置读取资源和模型。管理员必须从回复打开轮次调试，核对实际调用与提交结果；两端在生成中与失败时显示对应状态。

### 第三步：让预设、世界书、正则和实例参数真实生效

**真实预设导入与兼容补齐：** 执行 Agent 修复 `POST /import/preset` 对「梦鲸思客V4-0902」完整文件的大小限制，保持原始预设和扩展数据；执行 Agent 通过现有导入界面导入并绑定固定版本；管理端系统展示实际预设、世界书、正则、演绎者、模型及参数覆盖来源。执行 Agent 对照可读源码与本地已启用配置，提取会影响当前请求和输出的行为，复用已有组装、变量、任务与渲染能力，并补齐实际缺项；执行 Agent 完成管理端预设设置界面。验收按行为逐项记录，关闭功能与平台专用界面单列，原脚本保留作为来源资料。执行 Agent 对照[资源绑定检查](../character-authoring/linqian-prompt-binding.md)，确认角色及预设两组正则按阶段执行，实际请求已解析所用宏，模型请求包含正确的世界书与预设顺序，再用演绎者对白或行动完成真实续轮。完成条件同时包含公共导入接口通过、固定版本可重读、实际请求对照及真实模型记录；隔离数据库直接保存资源仅作为组装检查。本段的导入、固定版本重读、请求对照和真实续轮均使用「梦鲸思客V4-0902」验收；天琴座的联调结果按其预设版本独立记录。

**同步实现：** 执行 Agent 在后端扩展发布 schema 和解析器，固定资源版本及各槽位参数，并连接现有提示词、世界书和正则链路。执行 Agent 在管理端按编辑边界文档接入资源新建、导入、复制、编辑、保存和删除流程，在角色应用配置页提供选择、停用和有效配置查看。预设复用现有结构化编辑器，新建表单通过已有导入能力创建资源；世界书与正则补齐条目表单。正则测试按通道执行：保存、提示词和编辑通道通过后端实际处理器试跑，执行 Agent 在后端补齐相应测试接口；显示通道使用用户 Web 聊天所调用的同一显示处理模块。两种测试读取当前未保存规则、输入文本、位置、深度和变量，返回处理结果及逐条命中或跳过原因。资源保存与应用绑定分别提交；保存冲突保留输入。管理端同时提供完整 LLM 槽位、凭证维护、模型发现与测试、回合启停和校验失败策略。执行 Agent 在用户端为试聊和正式演绎实现[显示方案](role-status-rendering.md)定义的唯一消息与状态栏流程；用户端接收用于显示的规则和变量，管理端展示执行对照并提供返回聊天效果的入口。该能力属于本步完成条件。

**可视验收路径：** 管理员在界面新建对白预设并增删、排序条目，编辑包含“港口书店营业到午夜”条目的世界书，创建并试跑移除旁白标记的正则，保存后绑定这些资源，设置实例参数并发布 → 用户开启新对话询问营业时间 → 管理端查看该楼层的提示词解释、命中条目、有效参数及处理结果 → 用户看到对应回复。管理员再新建含凭证的 Profile，获取模型列表并测试连接，给 narrator 和 director 分别选择模型及参数，调整回合开关和校验失败策略后发布；执行 Agent 在运行记录中核对各阶段模型与处理策略。

**异常与边界：** 世界书和正则明确停用时仍可发布；选择已删除或不可读版本时发布失败并定位资源；实例参数越界时保持草稿可编辑；模型发现或连接测试失败时显示具体原因，管理员修正地址、凭证或模型后重试；缺凭证和启用阶段缺可用槽位时阻止发布并定位配置。固定标记的正则效果由确定性模型桩验证，真实模型的角色表现由执行 Agent 阅读判断。

**完成条件与证据：** 每项启用配置均有“管理端选择值 → 发布快照 → 楼层执行证据 → 用户可见结果”的对应记录。角色包编辑、媒体与 data 配置、包校验、版本交付及 Runtime 数据接入必须完成上文 R1 至 R7 中第三步的交付项。LLM Profile 修改测试还必须证明已发布模型参数遵循本方案的发布规则。验收记录必须包含凭证掩码、模型发现及测试结果、各槽位解析值、回合执行阶段和校验失败策略的实际分支结果。

**状态栏与正则的纵向验收：** 管理员分别编辑消息内及整屏 HTML/CSS 显示模板、变量绑定、剧情选项及显示正则，保存后进入用户 Web 试聊，再发布到正式会话。执行 Agent 按[显示方案验收清单](role-status-rendering.md#验收清单)逐步核对真实提交数据、布局、选项发送、历史快照及错误分支。正则的顺序、停用、深度过滤和未命中仍逐条验收；独立状态栏通过模板配置控制显示。管理端提供正文处理、变量提交、模板绑定与实际布局的关联记录。新会话使用新版本，旧会话保持固定版本。

**世界书的纵向验收：** 管理员配置常驻、关键词、辅助词、递归、指定深度、Outlet、停用和未命中条目，在用户端连续输入触发条件，再从管理端查看激活记录与提示词插入结果。Outlet 场景同时配置预设槽位；验收必须分别核对条目激活和最终插入，记录实际位置、深度及角色。

### 第四步：让管理员试聊、修正配置并发布通过验证的草稿

**同步实现：** 执行 Agent 在后端实现草稿校验，以普通 session 承载试聊，补齐应用、草稿修订和测试用途的关系及查询；试聊与正式创建共用发布配置解析器。执行 Agent 按编辑边界文档实现管理端的开始、继续、明确新建、改名、归档恢复和删除操作；管理端系统打开页面时只查询已有记录。执行 Agent 在管理端将现有聊天区域改为试聊记录与运行详情，提供继续试聊跳转、草稿有效配置、楼层解释、缺项跳转与发布操作，并按轮次调试文档接回历史 Explain、工具、变量记忆、分支及操作日志。执行 Agent 在管理端接入工作区 Agent 类型、项目绑定、启停、任务提交与取消。执行 Agent 必须在后端交付项目 Agent 与角色应用的关联 schema 和接口定义，写明允许参与的项目绑定、触发条件、配置解析及发布快照规则；前端按解析结果展示。用户端展示新发布角色的正式效果。

**可视验收路径：** 管理员从管理端打开用户 Web 试聊草稿 → 从消息返回管理端，在解释面板发现世界书未命中或预设不合适 → 修改并保存配置 → 明确用新修订新建独立试聊，旧试聊保持原修订 → 删除一条已结束的试聊并刷新核对 → 发布该草稿修订 → 用户建立新对话 → 管理端对照两个会话的解析配置。管理员再创建工作区 Agent 类型和项目绑定，停用后核对运行限制，启用后提交任务并取消尚未完成的任务；配置该绑定与角色应用的关联并发布，通过运行记录核对实际参与的绑定及配置快照。

**异常与边界：** 草稿缺项阻止发布；试聊生成失败保留输入和失败结果；发布时草稿修订已变化，管理端提示重新读取并验证；正式用户列表中只出现其正式会话。

**生成详情的数据接入：** 执行 Agent 先按[数据缺口文档](admin-generation-data-gaps.md)检查现有全部相关读取路径，为导演输出、完整提示词、逐阶段事件和历史执行尝试分别记录实际接口、schema、保存位置和关联标识。已有接口直接复用；执行 Agent 在后端补齐缺少的保存与查询能力，并同步更新 OpenAPI、SDK 和管理端。前端从后端记录读取内容，保留配置与执行结果的区别。

**生成详情的可视验收：** 管理员在管理端启用导演并保存配置，进入用户 Web 的试聊会话发送消息 → 从回复跳转管理端生成详情 → 查看导演实际输出、演绎回复和校验结果 → 查看该轮完整提示词及来源 → 展开工具参数与结果、变量暂存及跨作用域写入、记忆条目与维护任务 → 对一个失败轮次执行重试 → 按实际执行标识分别查看失败和成功记录。刷新页面后，已持久化记录仍能按同一会话、楼层及执行标识读取。执行 Agent 必须为每类数据保存对应接口响应与页面证据，逐项标注通过或需修改。

**完成条件与证据：** 试聊和正式会话使用相同配置时，解析结果一致。Agent 验收必须记录类型 ID、项目绑定 ID、任务 ID、启停及取消终态，并以关联 schema、发布记录和运行记录证明所选绑定及固定配置一致。真实模型的文本允许不同，验收以配置证据和 Agent 对角色效果的阅读为准。

### 第五步：完成新旧版本、停止发布和切换发布版本

**同步实现：** 执行 Agent 在后端完成发布历史、发布指针切换、资源引用生命周期及会话固定配置执行。管理端系统展示草稿与已发布配置差异、发布历史、停止发布和选择历史版本供新对话使用。用户端展示新建入口可用状态，并能继续自己的既有会话。

**可视验收路径：** 用户建立 v1 对话 → 管理员修改角色、模型或正则并发布 v2 → 用户继续旧对话并新建另一对话 → 管理端同时查看 v1、v2 会话 → 停止发布后尝试新建 → 切换到 v1 并重新开放入口，再新建对话。

**异常与边界：** 并发发布与创建会话时，单个会话绑定完整版本；被引用资源的删除操作返回具体引用对象；模型凭据轮换和模型参数修改分别按发布规则处理。

**完成条件与证据：** 执行 Agent 通过两端页面确认新旧会话对应版本，通过运行详情确认实际使用的配置。停止发布及版本切换的行为符合统一发布规则，刷新后保持一致。

### 第六步：完善长历史、生成失败与断线恢复

**同步实现：** 执行 Agent 在后端为用户入口连接现有 timeline、active-run、楼层结果和重试能力，补齐请求关联与重复提交处理。执行 Agent 在第二步的对话列表与继续能力上补齐历史分页加载、生成中状态、失败重试和断线后的状态查询。管理端系统在运行详情显示同一请求对应的会话、楼层和失败原因。

**可视验收路径：** 用户发送消息 → 模拟连接中断或模型错误 → 用户端保留输入/已提交消息并显示当前状态 → 管理员定位同一楼层 → 用户重新连接查询结果或重试失败楼层 → 刷新后继续会话。

**异常与边界：** 双击发送、响应已完成但流中断、生成仍在运行时刷新、历史超过单页、无会话空态均必须有可操作界面。前端必须先查询真实运行状态，再对支持重试的失败楼层提供重试。

**完成条件与证据：** 页面中的一次用户提交对应一次保存的用户消息；恢复和重试不会重复插入该消息。管理员看到的终态与用户看到的结果一致。真实运行中显示后端实际回复。恢复时必须关联原消息、执行终态和对应变量版本；显示处理及历史一致性按显示方案验收。

### 第七步：从资源创建或导入到用户可用，全程在界面完成

**同步实现：** 执行 Agent 在管理端将角色、预设、世界书、正则导入与编辑连接到角色应用详情，支持新建应用、选择资源版本、查看缺项并跳转修正。执行 Agent 在后端补齐资源引用、修订冲突与发布操作的对应结果。执行 Agent 在用户端完成角色列表、介绍、发布显示信息更新及空态。

**可视验收路径：** 管理员从界面新建或导入另一张角色卡，创建预设并编辑配套资源 → 创建新角色应用 → 编辑展示介绍 → 试聊并发布 → 使用者通过获准应用列表找到新角色并开始演绎 → 管理员修改展示内容并发布后，用户列表出现新内容。

**异常与边界：** 导入格式错误定位到文件；缺少必需配置定位到字段；资源更新后旧发布保持原版本；两个角色的会话历史清晰区分。测试使用者与模型凭据的初始准备可以由联调环境提供，角色配置和发布流程必须全部通过页面完成。

**完成条件与证据：** 执行 Agent 分别从界面新建资源和导入已有文件开始完成端到端演示，期间通过管理端完成所有角色配置，用户端始终无需配置 LLM、Profile 或正则。

### 第八步：两端独立构建后的交付验收

**同步实现：** 执行 Agent 为管理端和用户端提供独立构建入口及明确的 API 地址配置，使用同一个测试后端。部署方式复用届时已合并的仓库部署方案。联调启动、测试数据初始化与清理由显式命令完成。

**可视验收路径：** 执行 Agent 打开独立管理端地址和独立用户端地址，从角色配置、试聊、发布、邀请进入、演绎、更新、历史继续一直操作到停止发布；分别在桌面和手机视口重复关键用户操作。

**异常与边界：** API 地址错误、用户凭据失效、未授权会话、角色停止发布、生成失败、长历史、空列表均显示具体情况及可执行操作。用户端响应只提供展示字段、对话数据和显示方案规定的最小渲染数据；管理接口提供凭据引用、配置状态及掩码，以及内部提示词和管理执行记录；完整密钥由后端保存和调用。

**完成条件与证据：** 每条主流程均保存两端截图或录像、对应应用/发布/会话/楼层标识及测试结果；两个 Web 独立构建成功，涉及的类型检查、测试、Lint、OpenAPI/SDK 检查通过。此步骤在本地或已授权测试环境完成，线上发布另行安排。

## 验收清单

### 各步骤共用的记录要求

执行 Agent 必须为第二步至第八步分别记录：基线提交、测试使用者、操作入口、管理端动作、用户端动作、可见结果、关联后端标识、异常场景结果和结论。每份记录必须写清“通过”或“需修改”。第一步按其原型完成条件记录用户设计反馈。

后台接口测试、两端组件测试和端到端测试必须覆盖新增功能的正常、异常与边界分支。自动化断言仅验证结构、状态、归属、配置引用与确定性结果；执行 Agent 阅读真实模型的角色表现、提示词含义和交互文案。

执行 Agent 必须完成每步涉及的项目检查；只有新修改、检查失败或仍有具体问题时才扩大或重复检查。第一步原型同时保留交互检查、schema 与隔离联调证据，用户验收页面设计；正式步骤按上述要求独立验收。

### 最终成品完成条件

- 管理员可以在管理 Web 完成角色及其 LLM、Profile、预设、世界书、正则、HTML/CSS/JavaScript、媒体映射和预置数据的配置、发布和版本维护，并跳转用户 Web 试聊。
- R1 至 R8 及 M1 至 M5 的正式接口、存储、管理编辑与用户渲染均完成对应纵向验收，错误分支、历史读取和重启后持久化结果均有证据。
- 使用者可以在独立用户 Web 查看可用角色、开始演绎、继续历史并处理失败；页面无需用户填写内部生成配置。
- 后端可以从任意正式会话追溯角色应用发布记录及实际执行配置，并按发布规则处理版本更新。
- 两个测试使用者的会话归属分别正确；管理员可以通过管理入口查看所管应用的会话结果。
- 每个步骤的证据按“各步骤共用的记录要求”提交；业务语义由 Agent 阅读验收。
- 执行 Agent 检查试聊与正式演绎的代码入口，确认二者使用同一聊天组件、状态管理和消息处理模块；通过两种会话运行相同的发送、流式、重试、历史和显示规则用例。管理端只提供跳转及管理操作。
- 独立语义审阅 Agent 审阅方案及新增文案，主 Agent 处理意见后交付。

## 依赖与执行安排

当前方案与两个 HTML 原型没有新增外部依赖，也没有执行安装。第一步分别打开两个 HTML 文件。实施阶段优先复用仓库现有 Vue、Vite、SDK、生成服务与测试工具。

第二步的执行 Agent 在需要安装或为新应用声明外部包前，必须先提交对应安装清单：包名、准确版本、用途、安全公告核对结果及审计意见。现有锁文件包含多组版本，执行 Agent 必须以实际选用版本形成该清单并写入包管理文件；本方案不把现有锁文件等同于版本安全结论。安装执行范围以确认后的安装清单为准。

执行 Agent 必须按每步的目标文件完成管理端、用户端、后端与测试改动。用户确认并行实施后，再为实际参与的 Agent 分配文件所有权。

本计划范围之外的功能包括角色市场、支付、社交登录、多人共演，以及完整工作区治理、节点图编辑器和全部后台数据表管理的扩展建设。用户 Web 的注册、登录与账号资料按“必须要实现的目标”中的需求规格交付。现有管理 Web 端功能的保留要求按“两个 Web 的用途”执行。工具、MCP 与自定义状态的用户端配置入口属于后续建设；管理端已有入口及操作继续保留。

游戏业务模型、结构化游戏指令及后端游戏规则执行器属于未来需求；此前审计报告中的其他后台扩展能力按本计划八个步骤确定本版范围。
