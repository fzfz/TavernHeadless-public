# 生成过程追溯：正式分批实施计划

## 必须要实现的目标

本计划中的“执行 Agent”负责开发、测试和验收取证；用户端系统、管理端系统及后端系统执行各自的程序运行行为。工作项按目标文件和模块划分。

执行 Agent 必须在正式后端 `apps/api`、模型调用模块 `packages/core`、共享契约与 SDK、正式管理 Web `apps/web/src` 和正式用户 Web `apps/user-web/src` 中交付生成过程追溯及两端联合验收所需能力。本计划细化[两端与后端总计划](role-app-dual-web-plan.md)中的生成详情工作，并将总计划第二步的最小真实闭环与本计划首批合并交付。原型用于参考交互和核查已有接口；正式构建运行的两个 Web、API、数据库与持久资源文件共同构成交付成果。

原型成果位于 `/srv/tavern/TavernHeadless-role-app-prototype`。执行 Agent 必须保留该工作树已有成果，并在每批开始时记录实际实施工作树、代码基线与本批改动范围。

### 已确认的完整目标

以下要求由各批次共同完成，后续细则必须引用对应条目。

1. 执行 Agent 必须使后端记录一轮触发的全部后续任务及各自重试，并使管理端展示任务来源和所属轮次。
2. 后端必须为每次模型调用保存实际请求内容、模型参数、工具定义、响应、用量及错误。认证密钥仅用于请求认证，历史记录保存业务请求内容。
3. 执行 Agent 必须针对新轮次完成完整验收；管理端必须对旧轮次展示已有证据和具体缺失项，并单独展示当前配置预览。
4. 管理端详情页必须在运行中持续更新；后端必须支持在页面刷新和服务重启后读取已保存记录。
5. 后端必须为流式调用保存累计响应、开始时间、首个片段到达时间和结束时间；调用中断时必须保留已收到的内容及中断原因。
6. 管理端完整详情页必须以执行时间线为主入口，支持展开每次尝试的请求和响应，并保留现有分类面板。

每批的执行 Agent 必须将管理 Web 与用户 Web 的对应截图或录像、接口响应、会话及轮次标识、测试结果和明确结论保存到 `docs/plans/evidence/generation-trace/batch-N/`；其中 N 为上表批次序号。自动化测试验证结构和状态，执行 Agent 阅读两端页面内容与真实请求，判断对应关系和文案含义。

执行 Agent 必须先完成当前批次的验收，再细化下一批的具体字段、改动文件和测试用例。未通过项继续留在当前批次修正；已有完整目标的调整必须记录具体变化并由用户决定。

第三批的 Agent 接入对象、改动模块和专项验收由[第三批 Agent 调用记录补充计划](generation-trace-batch-3-agent-recording.md)统一定义。该补充计划与本页第三批的任务关系、公开状态及记忆注入验收共同构成第三批完成条件。

第一批执行 Agent 必须按[第一批实施计划](generation-trace-batch-1.md)开展工作；该文件统一维护本批角色绑定、目录职责、后端数据库与文件存储、接口、实施顺序及专项验收。

## 每批两端验收标准

执行 Agent 必须为每批分别填写管理 Web 和用户 Web 的验收表，再填写两端联合结果。每张表必须覆盖以下六项，并记录具体页面、操作、预期结果、实际结果、证据路径和“通过”或“需修改”结论。各批场景见下文“各批必验场景”。

| 验收项     | 执行主体、检查对象与通过条件                                                                                                                                                                                      |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 接口       | 执行 Agent 逐项列明本批使用的 HTTP 方法、路径、请求及响应 schema、错误码、权限和页面调用位置。执行 Agent 执行正常、异常及边界请求，确认两端实际调用这些正式接口，并核对保存结果、OpenAPI 和 SDK。                 |
| 业务逻辑   | 执行 Agent 核对两端的状态变化、允许操作、会话归属、发布版本及执行标识。发送、失败、重试、提交和历史读取必须符合本批规则；同一轮在两端显示的正文与状态必须对应后端记录。                                           |
| 数据可视化 | 执行 Agent 逐项核对页面文本、状态、错误、调用记录、任务关系及角色公开状态的数据来源；空态、加载态、成功态和失败态必须具有明确显示，页面记录与对应接口响应一致。                                                   |
| 布局       | 执行 Agent 按下文原型对照规则核对两端各验收视口的区域位置、宽高、间距、对齐、滚动容器、固定区域、遮挡和换行；布局必须与基线一致。                                                                                 |
| 像素级样式 | 执行 Agent 按下文原型对照规则比较字体、字号、字重、行高、颜色、背景、边框、圆角、阴影、图标和图片裁切。通过条件为每项样式符合基线，全部像素差异均完成核对和处理。                                                 |
| 交互       | 执行 Agent 对照原型实际操作导航、返回、输入、发送、展开与折叠、滚动、焦点、悬停、选中及禁用状态，并执行本批新增动作。触发条件、可用状态、反馈、跳转结果及返回位置必须符合原型，且操作后的数据结果通过前两项检查。 |

### 原型对照与像素级检查

基线登记采用以下原型入口。执行 Agent 必须按本批场景记录实际采用的页面与版本，并以对应共享脚本驱动的状态作为交互对照。

| 页面               | 原型入口                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------ |
| 管理工作区         | `apps/web/prototypes/admin-workspace.prototype.html`                                                               |
| 生成详情           | `apps/web/prototypes/generation-details.prototype.html`                                                            |
| 用户演绎与角色渲染 | `apps/user-web/prototypes/script-roleplay.prototype.html`、`apps/user-web/prototypes/user-roleplay.prototype.html` |

执行 Agent 必须在每批开工前锁定两端对应原型的文件、版本、页面状态和截图基线，并将记录放入该批证据目录。原型缺少本批场景时，执行 Agent 必须先补齐对应页面状态与交互，由用户确认后作为该批基线；正式页面按该基线交付。

截图基线必须记录浏览器及版本、操作系统、视口尺寸、设备像素比、缩放、字体、固定样例数据、滚动位置和展开状态。执行 Agent 必须在相同环境和状态下截取原型与正式页面；动画及流式页面必须固定到同一可复现状态。两端均须覆盖本批适用的桌面与手机视口。

执行 Agent 必须保存原型截图、正式页面截图、叠加图或像素差异图及逐项差异清单。执行 Agent 必须修正区域位置、尺寸和样式差异；渲染环境导致的差异必须在统一环境后重新比较。产品设计变更必须先由用户确认并更新原型基线，再按新基线检查。执行 Agent 必须阅读截图、判断差异并确认交互行为，图像比较脚本只计算确定性的像素差异。

固定样例用于复现视觉状态；每批联合业务验收另须按批次表使用正式接口和持久化数据完成。执行 Agent 必须同时提交视觉对照结果与真实两端操作证据。

## 验收清单

### 每批共同完成条件

- [ ] 当前批次的两端页面入口、联合操作流程和可观察结果均按批次表完成，执行 Agent 可以在后续批次尚未实现时复现该流程。
- [ ] 管理 Web、用户 Web 的六项验收表及联合结果全部通过，并提交本批各场景的原型与正式页面像素级对照证据。
- [ ] 两端正式页面、API 返回和数据库保存内容对应一致，刷新及重启后的读取结果具有两端证据。
- [ ] 本批新增接口的 schema、OpenAPI、SDK 和正式前端接入同步完成。
- [ ] 新增功能的正常、异常与边界分支测试，以及受影响模块要求的类型检查、Lint、构建和契约检查通过。
- [ ] 独立语义审阅 Agent 验收新增文档、页面文案和接口错误文案；执行 Agent 完成修正。
- [ ] 执行 Agent 按批次表后的证据规则提交结论；执行 Agent 记录当前完成批次、未通过项及下一批入口，供后续会话继续执行。

## 非本次目标

逐片段流式回放、依据当前配置补造旧轮次历史、自动恢复被强制终止的模型调用，以及线上部署属于本计划之外的工作。完整配置编辑、资源管理和发布版本维护继续按[两端与后端总计划](role-app-dual-web-plan.md)分批建设。

各批交付范围以“批次安排与独立可视验收”为准，首批具体边界由[第一批实施计划](generation-trace-batch-1.md#非本次目标)维护。

## 已获得的授权

用户已选定生成过程追溯方向，并确认本文“已确认的完整目标”。用户要求将工作组织为正式的分批实施计划，先打好最小框架；每批成果必须可独立验收、可观察且可视，并通过管理 Web 与用户 Web 联合验收，分别检查接口、逻辑、数据可视化、布局、交互和对照原型的像素级样式。

用户已明确要求将 Director、Verifier 和记忆处理 Agent 的调用记录接入工作补入后续计划，本计划将其列入第三批。

用户要求各批实施细则独立成文，总计划保留批次安排、共同要求及引用；首批已确认的配置和保存策略见[首批授权](generation-trace-batch-1.md#已获得的授权)。
