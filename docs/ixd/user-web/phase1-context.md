# 阶段 1：用户 Web 产品背景

## 1. 产品设计摘要

1. **TavernHeadless 用户 Web** 面向希望与角色持续演绎故事的使用者，提供选择角色、使用个人演绎人格、参与故事和恢复历史的浏览器入口。
2. 产品要解决的核心问题是：使用者能够理解自己正在扮演谁、进入哪个故事，以及如何接续已有演绎。角色卡通过前端 Runtime 呈现各自的故事体验，用户 Web 承担个人资料与演绎会话的管理。
3. 本次设计面向用户端。管理 Web 的角色创作、资源配置和发布工作由其自身设计资料管理。
4. 术语采用[用户演绎领域](../../../apps/user-web/CONTEXT.md)。具体产品行为见[需求规格](user-web-requirements.md)，需求来源和后端能力见[功能依据](feature-basis.md)。

## 2. 目标平台与实现基础

1. 产品类型为浏览器 Web。用户已确认桌面和手机浏览器同等重要，分别设计两套布局、交付两套原型，并分别验收。两端共享产品功能与业务规则，布局和操作方式适配各自的屏幕与输入方式。
2. 当前用户端基于 Vue、TypeScript 和 Vite，依赖仓库的 SDK 与共享模块；准确依赖版本以 [package.json](../../../apps/user-web/package.json) 为准。设计沿用现有实现基础。
3. 设计规范建议采用用户端自有规范，复用现有浏览器控件及 Runtime 能力。通用操作保持一致，角色内容允许表达各自的视觉风格。
4. 阶段成果和进度统一保存于 `docs/ixd/user-web/`。初步原型保留在其 `prototype/` 子目录，访问地址见 [progress.json](progress.json)。

## 3. 使用者与主要场景

1. **浏览中的访客**：尚未登录，希望了解可用角色及故事设定，判断是否开始演绎。主要需要容易理解的角色信息和明确的账号入口。
2. **准备开始故事的登录用户**：准备建立新的演绎会话，希望设计或选择个人演绎人格，并理解本次故事的起点。主要需要明确的身份归属和可用内容。
3. **继续故事的登录用户**：已经拥有历史会话，希望找到目标故事并恢复演绎，或整理历史记录。主要需要稳定的身份、完整的上下文和可辨认的历史。
4. 上述分类按当前使用状态划分。交互按使用者具备一般网页操作能力、无需了解引擎配置来设计；年龄分布和使用熟练度尚无用户研究数据支持。

## 4. 核心模块与优先级

1. **P0** 表示完成本次用户任务必须交付的核心模块；以下六个模块均属于此优先级。
2. **账号访问**：支持使用者注册、登录和退出，建立个人数据的访问身份。
3. **用户中心**：集中呈现当前用户资料与个人资源管理入口。
4. **角色选择**：帮助使用者通过筛选和角色信息找到希望演绎的故事。
5. **演绎人格**：支持用户设计和管理自己的多个人格，为不同故事选择扮演身份。
6. **角色演绎**：以独立页面承载角色 Runtime，支持用户与角色持续推进故事。
7. **历史管理**：支持用户找回、继续和删除自己的演绎记录。

## 5. 设计挑战

1. **角色表现与通用操作并存**：不同角色的内容和布局可以差异很大，使用者仍需辨认当前身份、会话状态和可用操作。
2. **多个人格与历史身份的连续性**：用户可能在不同故事中扮演不同人物，设计必须清楚表达人格资料与会话中实际身份的关系。
3. **长时间生成与故事阅读并存**：演绎存在生成等待、停止和失败，反馈需要让使用者理解进展，同时保持正文易于阅读。
4. **需求范围与已接入能力一致**：账号、筛选和默认人格等能力的接入状态不同，设计必须依据已登记的功能来源安排交付与验收。

## 6. 设计原则

1. **围绕开始与继续故事组织内容**：角色选择、人格管理和历史管理服务这两类任务，功能取舍优先考虑其对故事体验的作用。
2. **角色内容表达故事，通用操作保持可辨认**：用户 Web 的通用界面与角色演绎内容区按[需求规格第 4 节](user-web-requirements.md)划分职责。
3. **让使用者知道正在扮演谁**：涉及人格和会话的设计，统一依据[需求规格第 3 节](user-web-requirements.md)的人格归属及快照规则呈现身份。
4. **业务信息具有可追溯来源**：新增入口、统计、推荐或配置项按功能依据登记需求与数据来源；界面反馈对应实际可观察的状态。
5. **支持持续阅读和接续故事**：正文可读性、当前操作反馈和历史恢复的连续性优先于装饰效果。

## 7. 设计参考与视觉方向建议

1. **交互参考：SillyTavern**。按用户要求参考单个故事中的核心演绎交互；具体保留范围采用功能依据中的登记结果。
2. **视觉参考：当前初步原型**。以现有原型的温和、克制和重视阅读为建议方向，视觉细节在后续视觉阶段评审。
3. **色彩倾向**：通用界面采用温和的中性色与克制的强调色，角色内容的视觉表达由角色卡定义。
4. **字体气质**：通用文字清晰平实，故事内容重视长文阅读，标题可以适度表达叙事气质。
5. **视觉关键词**：克制、清晰、温和、阅读优先。

## 8. 设计约束

1. **产品范围**：核心模块以第 4 节为界，功能依据第 3 节记录当前范围外项目；运营、社交和商业化功能在提出对应需求后另行评估。
2. **技术与数据**：采用现有用户端、SDK 和 Runtime 的职责划分；各项后端能力及待联调项统一读取功能依据第 2 节。
3. **性能与反馈**：设计须考虑长历史、角色资源加载和生成等待。量化性能目标需在后续阶段结合真实资源及运行数据确定。
4. **设计资产**：目前可用资产为初步原型和示例角色内容，品牌规范及正式角色媒体资产尚未提供；视觉建议以第 7 节为准。
5. **业务与时间**：商业模式、上线日期和团队排期尚未提供，本阶段以已确定的用户任务限定范围。
6. **阶段交付**：本阶段确定产品背景与设计方向。阶段 2 的信息架构、后续流程、页面规格和视觉参数按各自阶段交付。
