# 更多角色卡样本对 API、卡格式与 Agent 的要求

本轮先做源码调研，[既有转换器计划](../../plans/native-card-converter/design.md)和[格式草案](../../plans/native-card-converter/native-card-v1.schema.json)保持原样。以下内容是基于样本的扩充建议，尚未获得实施批准，也尚未通过转换后运行验收。

## 调研范围与主要结论

截至本轮报告，已阅读六张 V3 成品卡、三份其他作者的卡片前端源码，以及两套独立 Quick Reply 作者工具。成品卡、拆分源码、配套工具分别统计；[脚本卡证据](samples-scripted.md)和[交互证据](samples-interactive.md)列出作者、固定提交链接、具体调用和覆盖缺口。API 判断来自[当前实现核对](api-findings.md)。样本集中于公开 GitHub 作者，代表已发现的机制，使用比例仍待更广泛调查。

**首批计划中的林茜、顾声慢两张卡不足以定义转换边界。外层 V2/V3 版本也不足以决定可转换性。** 这批样本包含状态结算、动态对象、开场初值、事件回调、世界书同步、辅助生成和宿主界面操作。转换器应把来源脚本表达的业务行为映射到本系统 API，再以实际执行结果判断支持程度。

建议优先支持这些卡中可复用的核心玩法：动态状态、带结果的界面动作、阶段剧情、开场初始化、状态到提示词的同步，以及有明确输入输出的辅助生成。任意插件原样运行、全局宿主页面模拟和无人值守自动多轮属于另外的产品能力，当前样本不足以支持将其列为通用转换的前提。

## API 扩充方向

以下列出功能契约，路由名和字段名留待设计阶段确定。

**角色动作提交。** 调用输入包含动作标识、输入参数、会话/分支、预期快照和请求标识。服务读取该卡版本声明的动作，计算候选状态、校验、提交快照并返回回执；需要生成时，回执与生成运行建立关联。界面消费物品、接任务、结算和选定开场都可以使用这一类能力。已有通用变量写入服务是基础，但角色动作还需要连接 schema、前值和显示快照。动作的幂等与并发前提需要显式语义，避免重复点击重复扣减。

**动态状态结构。** 在已有 set/remove 和精确路径控制上，研究受约束的对象新增、集合插入/移除及增量变更。每种操作需要明确缺键、数组索引、父子路径冲突及校验规则。整体替换父对象仍可作为作者显式选择，转换报告必须展示被扩大写入的范围。Zod 的默认值、强制转换、transform 和校验分别映射到初始化、标准化、派生和验证模块；编译器对具体语法逐项给出结果。

**事件与执行顺序。** 建议区分开场初始化、用户动作提交、提示词组装前、模型正文完成、状态提交后、分支切换与回退。条件模板返回提示词内容，计算函数返回状态结果，界面事件只更新展示；后端以显式阶段串联这些步骤。已有前端 DOM 事件和定时器可以复用，但它们与跨轮业务事件分别定义。

**会话知识与提示词投影。** 根据变量生成的人物资料应有明确来源与作用域。只读派生知识在组装时从当前分支快照计算；作者真正编辑的会话世界书则保存版本与差异。两种路径分别记录在转换报告中，并让 dry-run 展示该轮最终生效的知识及原因。

**辅助生成。** 卡声明每个辅助任务读取什么、使用哪个模型槽、输出何种结构、进入哪处存储、何时供正文使用。后端复用现有 Agent/任务执行器，前端只提交已声明的任务请求并读取进度。所有调用关联到同一动作、轮次或后台任务，预算与重试记录可查询。一次插件调用无需强制对应一种新的 Agent 类型。

## 自有卡格式应补充哪些表达能力

[此前格式草案](../../plans/native-card-converter/native-card-v1.schema.json)已容纳 worldbooks、state、agents、controllers、presentation 和 files；本轮样本说明还需要明确这些对象之间的行为契约，而不仅是增加文件字段。

- **能力声明**：逐项列出必需和可选能力及版本，例如动态状态、动作提交、单轮注入、知识同步和辅助生成；同时保留来源定位及转换结果。
- **动作与表单**：动作 ID、参数 schema、可用条件、读写范围、调用的计算模块、生成策略和界面绑定。开场表单单独关联到开场初始化及人设配置。
- **状态处理链**：初始化、输入标准化、Agent 提案、确定性计算、最终验证的顺序；动态集合和读写归属需要明确表达。
- **事件绑定**：事件阶段、读取的状态视图、调用的动作或模板，以及产出的用途；页面挂载与后端业务提交分别声明。
- **世界书执行规则**：声明式条件、时效和组内选择；会话知识覆盖层与卡的静态知识分别表示。
- **Agent 任务定义**：结构化输入、结果 schema、模型槽、依赖任务、调用时机、输出目标和预算配置引用。
- **资源与显示关系**：区分图片/音频显示、动态远程资源、媒体生成及多模态输入；逐类表达本系统提供的能力。PNG/CHARX 是输入容器问题，行为兼容性单独评估。

这些是待设计的语义要求。本轮保持原格式草案不变，避免在样本验证前固定新字段及版本承诺。

## Agent 应承担什么

| 工作                                               | 推荐执行者                                            | 理由                                                             |
| -------------------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------- |
| 阅读混合世界书、判断规则属于正文知识还是状态更新   | 转换审阅 Agent 提出逐项建议，由使用者确认             | 涉及语义判断；正则匹配只能提供定位证据。                         |
| 根据已发生的正文判断情绪、关系或事件事实           | 现有变量更新 Agent，按卡声明的输入输出扩充            | 这是语义提取，结果仍由 schema 和计算模块校验。                   |
| 加减数值、背包操作、概率采样、回合计数、阈值与去重 | 确定性动作和计算模块                                  | 减少随机生成对规则执行的影响，便于回放。                         |
| 规划下一阶段或生成辅助说明                         | 可选的剧情规划/辅助生成任务                           | 只在实际卡有需要时启用；已注册 Director 名称不足以证明满足要求。 |
| 从长期历史抽取持久知识                             | 可选记忆任务                                          | 确定性地把当前变量复制成人物说明时，直接使用知识投影即可。       |
| 检查转换是否保留行为                               | 测试程序核对结构与确定性结果，独立 Agent 阅读语义证据 | 两类验收共同覆盖功能，模型调用次数不作为兼容性证明。             |

## 是否值得支持及当前结论的限度

建议支持这批卡所体现的动作、动态状态、阶段模板、开场和知识同步，因为它们在不同作品中有具体用途，也能复用现有系统模块。建议将辅助生成作为可选能力接入现有 Agent 编排。建议继续收集群聊、多模态、自动多轮及更广泛 V2 作者样本，再决定相应产品范围。

当前证据支持“需要研究并扩充这些功能契约”，尚不支持“上述卡已经能够完整转换”。下一次验证应挑选行为差异明显的样本，分别比较输入、源行为、目标状态、dry-run 提示词和界面结果；明确标出直接转换、需语义重写、需补 API 和当前未研究四类结论。是否支持某张卡应依据其必需行为，使用者排除可选功能时也需要看到具体影响。

本轮没有安装依赖、执行外部脚本、导入实际角色数据或调用模型。正式实施仍等待用户决定。
