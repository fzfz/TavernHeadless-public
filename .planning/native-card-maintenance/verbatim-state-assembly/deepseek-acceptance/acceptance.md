# DeepSeek V4.1 Flash 真实角色卡验收

## 1. 验收结论

1. 验收于2026年10月5日至6日在独立分支 `codex/state-assembly-implementation` 完成。用户授权使用 `deepseek/deepseek-v4.1-flash`，费用上限为1美元。34次真实请求产生15轮已提交正文及15次已提交状态更新。
2. 四个组合分别使用林茜、顾声慢的完整角色资源，以及主状态预设、备用 MVU 状态预设。主方案分别完成林茜3轮、顾声慢8轮；两组备用方案各完成2轮。每轮正文和状态请求均先调用正式 dry-run 接口。
3. 请求传输、状态前值、快照归属及最近五轮变量历史通过结构验收。正文提交漏存完整世界书激活记录的问题已修复；修复后的两组真实样本均保存并复用了完整记录。
4. 真实角色卡验收结果为部分通过。林茜存在历史行为重复结算、照顾行为漏记及行动选项规则遗漏；顾声慢存在部分创作增量依据不足、时间格式错误及 GAL 格式错误。顾声慢页面仍显示开场并提示参数错误。
5. [账单汇总](billing-summary.json)确认调用费用为0.0612946533美元，账号用量增加0.061294641美元。四个未取得有效账单的请求继续保留0.1387659美元预算；确认费用与保守预留合计0.2000605533美元。

## 2. 实际配置与测试输入

1. [会话记录](cases.json)保存固定角色版本、开场、完整人设描述、预设版本及每轮成功结果。林茜会话绑定裴修远，顾声慢会话绑定周听澜。正文预设为天琴3.9，执行模式为 `compat_plus`，预设顺序选择100001，姓名前缀关闭；当前输入用绑定姓名标明动作主体，台词承接实际开场及此前正文。
2. 验收沿用此前真实测试的明确配置：`wi_format` 为 `{0}`，使角色世界书进入请求。其余完整导入资源及预设处理记录见[此前验收报告](../live-acceptance/acceptance.md)。本次完整人设实际进入正文和状态请求的结果见[结构校验](verification.json)。
3. [配置文件](configuration.json)记录模型、输出额度、供应商、费用限制及超时。首轮正文供应商为 DeepInfra；其状态请求因不支持 `uniqueItems` 失败。DeepSeek 官方端点未满足严格结构输出参数，返回404。随后15次成功状态更新均固定使用 Morph；正文共有12次 Morph 成功输出和3次 DeepInfra 成功输出。
4. 第29次正文请求在180秒后超时。第30次显式重试持续返回处理心跳，验收者终止独立验收进程并保存[终止证据](30-gushengman-primary-state-update-r8-body-retry-timeout-interruption.json)。之后正文固定使用 DeepInfra，状态仍固定使用 Morph。各请求关闭自动重试及供应商自动切换，模型始终使用用户授权的同一 ID。
5. 当前验收程序将配置的180秒总期限传给实际网络请求；处理心跳不能延长该期限。[保护检查](guard-checks.json)同时记录重启、重复请求、跳轮、错误状态轮次及证据重名的拒绝结果。

## 3. 请求、快照与历史的结构验收

1. [校验程序](verify.py)比较正式 dry-run 与实际供应商请求中的消息、完整人设和状态输出 schema，并比较供应商原始流、保存模型正文、公开正文及状态来源文本。15轮成功样本的这些比较均通过；公开正文按正文预设及正则处理后进入状态来源。
2. 每轮状态 `before` 等于上次提交的变量，`previousSnapshotId` 和提交结果的 `parentSnapshotId` 指向同一个前值快照。状态结果与正式角色视图一致；`sourceIdentity` 的运行、尝试、输出页和助手消息均对应成功正文调用记录。
3. 顾声慢主方案的变量历史长度依次为0、1、2、3、4、5、5、5。第七轮保留楼层2至6，排除楼层1；第八次成功正文位于实际楼层10，其历史保留楼层3至7，排除失败及未提交的楼层8、9。每项前值、后值和快照标识均与真实祖先状态一致。
4. 基线13轮的完整世界书来源记录为空，但条目 UID 已保存。修复补齐 `TurnCommitService` 的插入与冲突覆盖字段。修复后的顾声慢第8轮、林茜第3轮将完整激活条目及 UID 原样传入状态证据。状态组装仍按共享机制扫描世界书；顾声慢首轮的新正文提及社团人物，因此状态扫描另外激活条目4，正文来源记录保留生成时实际使用的条目。
5. [结构校验](verification.json)记录533项通过、13项基线缺陷及0项当前失败；两组修复后完整样本的91项检查全部通过。旧样本保留修复前结果。[代码阶段记录](source-stages.json)及[修复补丁](source-patch.diff)区分原提交与修复后的请求。
6. 本次角色资源没有触发 `getvar::stat_data` 的正文宏路径。该路径的确定性验收见[实施验收记录](../implementation-acceptance.json)；本次真实请求验证的当前状态入口为状态数据源中的 `before`。

## 4. 人工语义验收

### 4.1 林茜

1. 主方案及备用方案前两轮均保持姓名、夫妻身份、第三人称叙述和直接引语归属。模型通过丈夫的现场发言使林茜得知自己被发现，知情变化有具体传播途径。
2. 主方案第1、2轮分别将堕落从80增加到95、再增加到110。实际正文只有开场动作的中断、回述及旧痕迹处理，状态提案却分别计入新的飞机杯、直接接触及体外射精；第2轮历史又明确显示此前已经结算。备用方案第1轮存在相同重复结算，第2轮新增行为数组为空，堕落保持95，其本轮增量正确。
3. 第2轮两组提案都将照顾增量写为0。主方案正文已写丈夫递纸巾并等待，备用方案已写擦去水滴、避免受凉及准备吹头发，原卡照顾条件已满足。两组最终感情仅减1，因此完整结算未通过。
4. 主方案第1轮地点写为“拆迁旧楼二楼楼道口”，并附注林茜跟随丈夫离开房间、正往楼道口走；正文此时只写丈夫要求她跟上，尚未写出她跟随的行动。备用方案第1轮正文仍在单元门口，状态却写成夫妻家玄关。第2轮两组地点分别与旧楼楼道口、家中浴室的正文相符。备用方案心声另将计划询问小龚、艾沫沫写成已经询问，实际正文尚无通话结果。
5. 实际状态请求缺少原卡第115条完整规则及行动选项各序号用途。两组第2项选项多由林茜行动，未保持该序号由裴修远追问、查证或现身的用途。重复结算已经违反实际 `factsSchema` 中的本轮新增限制；原卡规则遗漏属于迁移配置问题。
6. 逐轮正文、提案与结果分别见主方案的 `r1` 至 `r3` 文件及备用方案的 `r1`、`r2` 文件。备用方案第1轮遗漏开场姿势及照片位置的动作承接；主方案第2轮存在时间线冲突，并让用户角色离场；主方案第1、3轮及备用方案第2轮由用户角色台词结尾。

7. 修复后的主方案第3轮保持堕落110，符合本轮没有新增性行为的正文；时间增加50分钟，最后地点为裴修远办公室，与正文明确时刻及移动相符。感情提案仍漏记丈夫返回、递纸巾和等待的新增照顾，感情减少1点的本轮依据较弱；心声也未承接本轮小刘倒掉杯中水、洗净杯子的说明及杨桃子的新消息。

### 4.2 顾声慢

1. 两组方案的前两轮保持人物姓名、第三人称叙述及台词归属。主方案第2轮进入活动室、按新半拍建议试奏并确认成功，情感增加2、创作增加4均有本轮依据。备用方案第2轮在走廊形成新编曲理解，尚未进屋；其情感增加2、创作增加4和地点保持走廊也有依据。
2. 主方案第1轮创作增加4，正文主要回顾开场既有突破，缺少本轮明确的新灵感或部员练习依据；初始创作值仍为0，与开场已有突破存在配置矛盾。主方案第3轮创作增加3也缺少新增触发条件；第6轮重奏既有方案，创作再增加4的依据较弱。
3. 主方案第4、5、7轮分别形成新的创作理解、留白与小提琴接入方案、轻量主旋律回归方案，其本轮创作增量有依据。情感增量可对应实际支持与倾听；累计值仍继承此前未通过的增量。
4. 时间字符串持续缺少日期与时刻之间的空格。主方案第2轮场景切换只增加15分钟，未达到实际启用规则的20至40分钟默认值。后续短试奏与“社团活动”时长的适用范围未明确，普通对话的15分钟增量不能代表所有活动时长已通过。
5. GAL 正文持续存在首个指令为 `bgm`、重复完整立绘名、指令前缺少注释、CG解除时机错误及夜景继续使用黄昏背景的问题。第4轮起，正文已包含 `<Check>`。
6. 第3轮正文将模型资料中的角色姓名当作周听澜已知信息；第4、7轮对相识时长的叙述与会话时间不符。第4、7轮心声分别为77、66个字符，汉字数为51、58；原卡“60字”未定义英文及标点计数方式，长度结论受该口径限制。

7. 修复后的主方案第8轮情感增加2，依据是周听澜本轮的理解与支持；创作增加4，依据是顾声慢为曲子新增了一个采用单音的后段，并完成该后段的试奏与记谱。心声为68个字符、62个汉字，按两种计数都超过原卡60字限制；时间格式和部分 GAL 格式错误继续存在。

## 5. 实际页面显示

1. [浏览器程序](browser.mjs)加载当前构建的 user-web，通过跨域正式 API 获取角色视图。页面 URL 固定选中验收快照，程序等待角色视图与 Shadow DOM 就绪，再保存 API 身份、DOM、网络状态及截图。
2. 林茜两组页面可显示已保存正文和已提交状态。截图及 DOM 文件分别以 `linqian-primary-state-update-page`、`linqian-backup-mvu-state-update-page` 命名。
3. 顾声慢两组页面显示开场，并提示“提交参数无效，请重新发送”。角色脚本 `main.js` 向 `messages.getFloor` 传入了当前契约不接收的 `attemptId`，还调用了当前 Runtime 未提供的 `variables.getFloor`；正文及状态已通过正式 API 保存，角色脚本仍未能读取并显示本轮正文。对应证据以 `gushengman-primary-state-update-page`、`gushengman-backup-mvu-state-update-page` 命名。

## 6. 回归检查与证据读取

1. 新增保存回归测试先复现插入与覆盖两条失败分支，修复后36项定向测试通过。全量测试覆盖562个文件，5176项测试通过；类型检查通过；lint 检查产生0项错误和4项既有警告。生产修复通过独立 Standards 与 Spec 审查。
2. 供应商请求、原始响应及账单按实际调用序号命名。每轮参数、正式 dry-run、成功结果及公开消息按组合和轮次命名；带变体名称的文件保留显式重试。`model-call-records.json`、`state-snapshots.json` 保存对应数据库证据。
3. 复核结构结果时，在本 worktree 根目录运行 `python3 .planning/native-card-maintenance/verbatim-state-assembly/deepseek-acceptance/verify.py`。程序单独报告基线缺陷，并要求两组修复后样本完整存在。
4. 凭据与隔离数据库位于本机配置及被忽略的临时目录。重新启动已保存的验收环境必须设置 `ACCEPTANCE_RESUME=1`，程序继续使用累计费用与既有会话；新的真实调用仍受[配置文件](configuration.json)的总预算约束。
