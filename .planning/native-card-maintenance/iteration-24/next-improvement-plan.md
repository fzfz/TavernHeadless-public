# 下一次转换改进方案

## 1. 总目标

1. 计划执行者完善现成的确定性工具，减少转换Agent的重复阅读和临时代码生成；转换Agent继续负责语义判断。
2. 下一次独立转换保留有效原文、按源顺序应用开场初始化，并正确恢复前端发送状态。
3. 验收负责人分别记录转换、维护和正式验收耗时，以20分钟生成及30分钟完整转换为效率目标。

## 2. 现状调研

1. 本轮原始转换的13项检查为5项通过、6项失败、2项未执行。具体问题和证据见[验收报告第2、3章](acceptance-report.md#2-原始产物的问题及根因)。
2. 现有begin返回完整任务路径和预检结果；read返回文件路径，但每次调用覆盖同一读取文件；parse已支持Agent选定的JSON或YAML片段。
3. 现有copy可复制原文片段；map-entry可批量复制条目正文。Agent仍临时编写约36KB生成代码，并改写状态规则文字。
4. 共享初始状态校验已修复；模块加载器及状态提示组装已经完成本轮联调。

## 3. 面临的问题

1. 读取结果会被下一次read覆盖，并行调用使Agent混淆当前内容；begin的长数组被宿主截断。
2. YAML解析工具不能应用随后出现的源初始化操作，Agent容易遗漏覆写。
3. Agent混淆状态结构约束与发送时点检查，并用摘要替换有效规则；额外摘要还能绕过源条件。
4. 选项发送锁只在原发送Promise中恢复，系统聊天组件的成功重试不能解除该锁。
5. 一次供应商拒绝uniqueItems；另一模型在参数修正后耗尽输出额度，结果为空。实际状态提案验收尚未通过。

## 4. 解决和实施方案

### 4.1. read和begin的结果交付

1. 给Agent的帮助：read为每次读取保留独立文件；begin按类别交付完整待判断索引，Agent能识别已复制字段和当前待处理内容。
2. Agent传入的数据：read沿用taskFile和源JSON Pointer；begin沿用单个PNG或JSON输入。Agent按返回的绝对文件路径读取结果。
3. 返回数据：read保持contentFile、linesFile及类型信息；begin返回各类数量和完整结果文件路径。已写入字段、待判断内容和结构诊断分别交付。
4. 计划执行者实现：read在本次任务目录内创建独立读取子目录，保存该次内容与行范围；begin将现有结果数组保存到本次任务目录，控制终端输出长度。脚本只处理路径、字段定位和类型，不选择内容用途。
5. 联调验收：连续与并行read的返回路径均对应各自源值；长脚本不出现在终端正文；Agent能从begin完整索引找到全部pending项。

### 4.2. 开场初始化操作

1. 给Agent的帮助：现成工具按Agent选定的顺序应用源初始化数据及源操作，避免Agent临时编写数组覆写代码。
2. Agent传入的数据：taskFile、初始化目标文件，以及源字符串Pointer和明确片段范围。Agent指定片段属于JSON/YAML数据还是初始化操作数组。
3. 返回数据：工具返回实际写入的目标文件和解析或操作错误；错误指出操作序号、路径和不满足的类型。
4. 计划执行者实现：复用parse的片段读取；新增初始化操作命令，按源顺序处理源协议已有的replace、delta、insert、remove、move。操作的含义取自源协议；未知操作报告错误。该命令不判断初始化块是否有效，不从故事推算初值。
5. 联调验收：begin、read、parse和初始化操作连续执行；验证数组覆写、嵌套路径、序号变化及源协议错误分支，并与正式初始状态校验联调。

### 4.3. 原文写入和前端发送时序

1. 计划执行者以[现有语义参考第1至3章](../../../.agents/skills/native-card-conversion/references/semantic-experience.md)为转换判断依据。
2. 转换Agent选定源位置后，使用现有copy或map-entry写入完整文字；代码改写依据正式API，保留源条件、执行顺序及结果。
3. 计划执行者补充通用前端示例，使用正式楼层提交回调解除发送锁，并按当前快照刷新按钮。示例同时处理直接发送成功与系统组件重试成功。
4. 验收负责人检查原文、条件和初始化覆写，执行发送失败、组件重试、再次点击、历史切换和回到当前状态的连续流程。

### 4.4. 真实状态模型验收

1. 验收负责人从正式可用免费模型目录选择支持当前结构化输出schema的模型；请求保持正式schema。
2. 验收负责人先保存状态dry-run，核对独立预设、源规则、聊天历史、本轮成功消息、变量历史和前值，再按既有免费模型额度调用。
3. 供应商继续拒绝当前schema时，验收负责人保存原始错误，分别记录供应商限制与正式接口错误展示问题，并提出具体API改动方案。

## 5. 方案待决策项清单

1. 本方案尚未实施；新增初始化操作命令及读取交付调整留待用户决定下一次工作范围。
2. 是否调整正式API：验收负责人先用支持当前schema的现有模型核对供应商限制，再根据实际响应提出具体修改内容。

## 6. 计划验收清单

1. 计划执行者先完成各阶段确定性测试，再运行与前序命令及正式接口的联调。
2. 仅派发一次新的干净上下文转换，任务消息沿用用户规定的Skill与单个源文件格式；验收负责人不追加指导。
3. 验收负责人分别检查原文、开场初始化、状态规则条件、格式及正式导入回读，保存失败项的实际产物及逐项结论。
4. 发送失败恢复后，选项按钮实际发出请求；历史状态选项禁用；资源失败与代码错误分别记录。
5. 验收负责人按宿主记录的阶段起止时间计算经过时长，包含Agent分析和调用间隔，核对第1章的效率目标；超时后按调用间隔、重复读取和临时代码规模复盘。
6. 验收负责人单列[跨轮完成条件与标签范围](../iteration-23/main-acceptance-cases.json)中的F01、F02真实模型结果。

1. 本方案不增加转换记录门禁、hash校验、程序语义判断或卡片专用生成器。
2. 本方案不调整模块额度，不实现包自定义工具、独立手机会话或原子剧情与变量恢复。
