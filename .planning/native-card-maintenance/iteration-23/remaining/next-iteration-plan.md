# 单卡转换 Skill 改进方案

## 1. 总目标

1. 转换 Agent 从用户指定的单个 PNG 或 JSON 角色卡生成符合当前 API 的原生 ZIP。人物、剧情与变量规则保留原文，HTML、CSS 和程序按目标模块契约调整。
2. 维护负责人修订读取和写入范围，阻止旧卡产物进入本次转换，保证应用运行配置保持原状。
3. 维护负责人接入已合入 main 的状态 Agent 实现，迁移源规则的生效条件，并完成正式导入、回读及核心运行验收。
4. 转换 Agent 负责源卡判断、包文件生成、包检查和打包；维护负责人负责 Skill 维护、系统同步、运行验收和提交。

## 2. 现状调研

### 2.1. 输入路径和旧产物读取

1. [派发记录](single-trial/dispatch.json)显示，唯一一次测试使用 fork_turns="none"，消息包含完整 Skill 路径和完整源文件名：`.tmp/native-card-inputs/USER002-v1.3.32/input.json`；执行期间没有追加指导。
2. begin 返回了该文件对应的 taskFile、sourceFile、packageDirectory 和 outputDirectory 绝对路径。转换 Agent 随后主动搜索 `apps/web/prototypes/characters/linqian`，读取旧 source-card、转换映射和模块，并将旧 schema、derive、validate 复制进本次包。
3. 测试前的 SKILL.md 已要求单个输入及两个写入目录；提交 b9d461f 没有删除这些要求。原文未明确限定其他卡产物的读取范围，Agent 将旧文件当成了可复用的实现依据。begin 返回路径不会限制宿主文件工具的访问权限。

### 2.2. 写入失败和运行配置改动

1. b9d461f 已修复包内绝对路径写入和命令失败返回，并增加选定条目的批量写入。133项实际源卡写入及733项转换器测试通过，见[修复检查](../path-failure-fix/checks.json)。
2. 转换 Agent 在默认预览失败后，把 `apps/api/config/native-card-module-runtime.json` 中的 maxModuleFiles 从128改为256。该动作超出了原有写入范围；主代理中止执行，退出处理恢复了原配置，见[只读边界记录](single-trial/termination-and-boundary.json)。
3. 原 Skill 同时要求转换 Agent 生成 ZIP、正式导入和运行预览。用户现已明确转换 Agent 的目标仅为 ZIP，本方案按第1章划分执行职责。

### 2.3. 状态 Agent 与模块加载现状

1. origin/main 的 88722f36568a5b098bb9974a6999c524679c081c 已合入 PR #13。正式状态更新采用独立预设和共享提示词组装器，支持对话历史、变量历史、当前消息、规则、前值、工具证据与输出契约，并提供状态 dry-run。
2. 当前开发分支已通过合并提交595bf26接入该提交。主代理已恢复 state-update-service.ts 的本地优化，并解决 backend-api.md 和 state-update-api.md 的恢复冲突；检查状态见 ../../main-sync-2026-10-06/status.json。
3. 新 StatePromptService 仍按 ruleFiles 顺序连接全文；它不会自动恢复源脚本对规则的 if 条件。该问题需要转换规则和预设配置共同处理。
4. origin/main 的 RoleModuleLoader 仍收集全部 server_script JavaScript 和 data JSON。测试包有148份此类文件，其中133份为世界书条目；默认128文件上限导致会话创建失败，见[默认预览失败](single-trial/default-preview-failure.json)。

## 3. 面临的问题

### 3.1. 转换 Agent 读取了本次输入以外的卡内容

1. 输入路径和 begin 返回值完整，但 Agent 主动使用旧试产卡的规则和程序，造成源版本混用。
2. Skill 需要同时明确允许读取的内容、当前任务路径和只读参考资料，不能仅说明传入哪个源文件。

### 3.2. 转换 Agent 修改了应用配置

1. 转换 Agent 为继续预览提高了系统额度，违反了包目录和任务目录的写入范围。

### 3.3. 状态规则失去了源生效条件

1. 源脚本仅在 E032=true 时读取条目105；目标将该原文常驻配置到 ruleFiles。
2. 目标 derive 又仅凭 routeRulesLoaded 接受路线变化，主代理已复现 E032=false 时仍发生变化。这是规则输入和程序转写问题，本次未取得真实状态模型输出。

### 3.4. 正文附带变量更新块的要求没有删除

1. 源条目108要求每次正文附带 UpdateVariable 块，并以其结束标签收尾；这些要求属于源 MVU 的正文格式。
2. 源条目109同时包含 Analysis、JSONPatch 的格式要求，以及当前值来源、缺失值保持和行动选项生成要求。目标保留了整条，却没有将其中有效规则提供给状态 Agent。

### 3.5. HTML、CSS 和程序没有按当前接口转换

1. 转换 Agent 重写了源 HTML、CSS，并复制旧原型程序。首次包校验因此返回22项模块问题，包括导出、导入、Date 和 structuredClone 使用问题。
2. 包格式修正通过与源行为保持需要分别验收；复制旧程序不能替代按当前 API 改写。

### 3.6. 系统把未被模块导入的世界书文件计入模块额度

1. ZIP 已通过正式导入和155文件回读，但会话创建时，系统将148份包内资源交给模块 worker，超过128文件限制。
2. 世界书 JSON 的数量影响了不依赖这些文件的模块加载。这是系统加载器的计数范围问题，转换 Agent 修改运行上限不能解决该架构问题。

## 4. 解决和实施方案

### 4.1. 修订转换范围与 ZIP 流程

1. 维护负责人已在 SKILL.md 的文件读写范围中限定转换内容来源、本次任务路径及允许读取的参考资料；旧试产卡和其他任务产物不参与转换。
2. 维护负责人已将转换流程收束为 begin、read、语义判断、确定性写入、index、validate、pack 和 ZIP 交付。转换 Agent 对命令失败采用 tools.md 第2章的处理方法。
3. 维护负责人已将 formal、preview 及其验收资料的执行主体统一为维护负责人。转换 Agent 对应用源码、运行配置、环境变量、依赖和服务权限保持只读。
4. 维护负责人通过实际读取和写入记录验收边界。本方案不增加文件访问门禁、转换记录门禁或 hashing 校验。

### 4.2. 接入 PR #13 并同步只读资料

1. 维护负责人核对当前分支、未提交修改和 PR #13 的合入提交，在当前 worktree 逐文件保留既有修改后合并该提交；冲突按正式接口和本地修改目的分别处理。
2. 维护负责人执行状态组装、状态更新、角色发布和状态 dry-run 的现有测试，确认 profile.presetRef、会话固定预设及历史配置使用正式实现。
3. 维护负责人同步正式 backend-api、state-update-api、state-prompt-assembly 及相关 schema 的 Skill 内置只读副本，更新 API 来源清单、架构第2.2节、目标格式说明和读取入口。全部资料与当前工作区实现一致后，再派发转换测试。
4. updaterPrompt 在新实现中仅保留包格式兼容作用，不能作为状态模型的实际任务提示。

### 4.3. 转换规则的生效条件和变量变化

1. 维护负责人在[语义判定经验](../../../../.agents/skills/native-card-conversion/references/semantic-experience.md)中要求转换 Agent 一起读取规则正文与调用它的 if、变量、比较条件及辅助函数，确定原文应在何时提供给哪个模型。
2. 无条件状态规则可以进入 ruleFiles；受变量条件控制的原文通过状态预设中的世界书组装和正式提示控制器提供。维护负责人先核对这些接口能否实现源条件，再确定条目、控制器和预设的配置。
3. 维护负责人为条目105分别建立 E032=false 和 E032=true 的隔离输入，通过正式状态 dry-run 核对最终 messages 中的规则原文；条件不成立时没有该规则，成立时取得完整原文。
4. 维护负责人分别核对 derive 的输入条件和 validate 的业务约束，确认 E032=false 时不能产生该路线变化。模型给出的 routeRulesLoaded 标记不能代替源状态条件。
5. 现有组装接口若无法把源条件作用于对应模型，维护负责人记录实际请求、已检查接口和缺失行为，提出具体 API 方案；程序校验不替代状态 Agent 所需的规则输入。

### 4.4. 删除正文变量块的格式要求，保留有效规则

1. 维护负责人在 semantic-experience.md 统一使用具体名称：正文附带 UpdateVariable、Analysis、JSONPatch 的格式要求，以及正文输出状态栏标记或页面代码的要求。
2. 维护负责人在语义判定经验中要求转换 Agent 删除纯格式要求，将混合内容中的有效规则原文写入状态预设读取的规则文件或世界书条目。下一次测试分别核对条目108的删除，以及条目109中的当前值来源、缺失值保持和行动选项生成要求的原文保存。
3. 维护负责人在语义判定经验中要求转换 Agent 删除仅用于隐藏或修复上述变量块的正则，按实际用途保留仍承担有效文本变换的部分。转换决定采用语义判定经验第6章的规则。

### 4.5. 按当前模块 API 改写页面与程序

1. 维护负责人已在 SKILL.md 中明确 HTML 挂载、CSS 作用域、模块入口、资源引用、具名导出、导入格式、上下文参数及允许全局对象的 API 读取入口。
2. 转换 Agent 保留源有效文字和页面内容，仅为目标 API 所需结构改写 HTML、CSS；程序按当前接口转写输入、条件、分支、顺序和结果。
3. 维护负责人核对 backend-hooks.mjs 和 run-backend.mjs 等内置通用示例与当前 API 一致，并在 sources.md 标明其读取时机；具体角色卡旧程序不作为示例。
4. 转换 Agent 在打包前通过正式包校验；维护负责人再用源分支输入比较目标模块结果，并检查原文及必要页面结构改动。

### 4.6. 按实际依赖加载后端模块

1. 维护负责人修改 RoleModuleLoader：从当前入口沿合法静态导入递归收集 JavaScript 和 JSON，只将实际依赖交给 worker。
2. 已声明文件、用途、目录、静态导入和路径约束继续由正式校验处理；动态导入、外部模块和主机文件访问沿用已有拒绝规则。
3. maxModuleFiles、maxModuleBytes、maxInputBytes、执行期限和并发额度保持现值。模块文件及模块字节额度按实际依赖集合计数，输入字节额度继续约束传入的状态与世界书。
4. 维护负责人更新正式后端文档及对应只读副本；角色包不获得修改系统额度的权限。

4. 维护负责人检查正文变量块要求的删除、有效规则原文、条件分支和当前 API 格式；转换器检查和 ZIP 正式导入、逐文件回读分别记录。
5. 接入 PR #13 后，维护负责人保存状态 dry-run 的实际请求和 messages，分别检查状态预设、规则、历史、来源消息、前值和输出契约；再按已有模型授权验证状态生成。

8. 维护负责人按[执行改进方案第1章](../execution-improvement-plan.md#1-总目标)记录20分钟文件生成阶段。本次转换 Agent 的总耗时从宿主会话启动计至交付 ZIP 的最终答复，目标为30分钟；正式导入及运行验收另计耗时，完整维护总耗时单列。
