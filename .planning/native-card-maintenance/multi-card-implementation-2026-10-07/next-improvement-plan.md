# 五卡抽样后的修复计划

<!-- markdownlint-disable MD013 -->

## 1. 总目标

1. 计划执行者修改转换 Skill，使转换 Agent 保留有效规则原文，使用一致的状态判据，减少模块接口修正次数。

## 2. 现状调研

1. 本轮新增静态 replace 数组覆写能力，78项 CLI 测试通过。五张卡均由独立干净上下文队员执行；四张交付 ZIP，一张因源文件缺少规则正文停止。
2. 上一版林茜转换耗时460.321秒；本轮第二次转换耗时1182.918秒，第三次耗时1923.918秒。源文件和单句派发要求保持一致。
3. 正式导入及文件回读成功不能证明规则保留正确。独立验收仍发现有效规则被删除或改写。

## 3. 面临的问题

1. 林茜的混合格式条目包含有效英文规则。转换 Agent 删除了其中部分规则，并将部分规则翻译、改写为中文指令；第三次转换还把规则包装为新写的 JSON。
2. 林茜第三次转换的提示控制器把36个事件值写成代码字符串。该模块语法有效，实际输出却没有包含事件布尔值。
3. 人妻卡的变量公式原文被改写，状态 Agent 和后端模块都能改变同一计算结果，存在重复计算风险。
4. 双面恋人前端根据合并亲密度是否为 null 判断身份模式，后端根据新增布尔字段判断。两个条件可以给出不同结果。
5. 转换 Agent 反复修正模块导出、上下文和返回格式，耗时增加。当前包检查只验证程序契约，不能代替计划执行者阅读规则。
6. 免费模型实际返回了正文，但状态输出分别遇到 json_schema 格式拒绝、uniqueItems 语法拒绝或无返回。林茜正文请求返回供应商400，具体原因尚未确定。
7. 林茜第三次转换还丢失了终局路线重选例外及行动选项缺失项恢复。后端未去除选项首尾空白，前端去除后发现重复并禁用整组。
8. 两份正式状态 dry-run 的最终消息已包含六个状态来源，追踪却把对应 marker 标为未解析；导入报告的诊断未反映状态运行时的实际展开。

## 4. 问题的解决和实施方案

### 4.1. 修正规则原文写入方式

1. 计划执行者修改 `SKILL.md` 第3.2节的写入指令，将下列内容加入原文写入步骤：

   ```text
   转换 Agent 使用 copy 将仅供状态 Agent 使用的选定规则原文写入状态规则文件。规则中的旧标签和输出操作需要调整时，转换 Agent 只修改这些格式片段，保留其余原文的语言、条件和例外。转换 Agent 写完后逐段对照源文，确认每段保留内容仍在目标文件中。
   ```

2. 计划执行者修改 `references/conversion-map.md` 的状态规则行，明确规则正文使用该行规定的 UTF-8 文本文件。状态输出格式说明由独立状态预设及正式输出契约提供。
3. 计划执行者修改 `references/semantic-experience.md` 的混合格式条目规则，删除与[SKILL.md 第3.2节](../../../.agents/skills/native-card-conversion/SKILL.md#32-写入文字和状态内容)重复的写入方法，保留“哪些内容有效、哪些格式删除”的判断依据。
4. 计划执行者完成独立语义审计，再以新干净上下文队员复测林茜和人妻卡。计划执行者逐段检查英文规则、变量不可读时的条件、选项生成例外及公式原文。

### 4.2. 修正控制器状态序列化

1. 计划执行者在 `references/semantic-experience.md` 的动态提示规则中加入：

   ```text
   转换 Agent 编写变量列表控制器时，将实际变量对象序列化为文本。转换 Agent 调用控制器，检查输出中的布尔值、数组和对象是否与输入状态一致。
   ```

2. 计划执行者复测林茜时，使用实际初值及只改变一个事件标记的状态分别运行控制器，保存两个实际输出。输出必须包含对应的 false 和 true。

### 4.3. 统一变量计算的执行主体

1. 计划执行者在 `references/semantic-experience.md` 的计算规则中加入：

   ```text
   转换 Agent 为每个计算结果选择状态 Agent 或后端模块负责写入。后端计算的结果配置为派生路径；状态 Agent 提供该计算需要的事实输入。
   ```

2. 计划执行者复测人妻卡时，检查状态 profile 的可写路径与派生路径，确认公式结果只有一个写入主体；再用源公式的各行为分支与目标计算结果逐项对照。

### 4.4. 保留业务校验例外

1. 计划执行者在 `references/semantic-experience.md` 的业务校验规则中加入：

   ```text
   源规则含例外条件时，转换 Agent 在校验模块中保留该例外。例外依赖本轮剧情判断时，状态 Agent 通过 facts 提供判定事实，校验模块按该事实选择对应分支。
   ```

2. 计划执行者复测林茜时，分别提交没有重选事实和包含用户明确重选事实的终局路线变化，确认校验模块分别拒绝和接受。

### 4.5. 统一前后端状态判据

1. 计划执行者在 `references/semantic-experience.md` 的状态显示规则中加入：

   ```text
   同一个状态模式同时影响前端显示与后端计算时，转换 Agent 让两者使用相同的判定字段和条件。
   ```

2. 计划执行者复测双面恋人时，分别检查未揭晓、已揭晓及旧包曾出现的冲突状态；前端显示与后端计算必须选择同一种模式。

### 4.6. 减少模块接口修正

1. 计划执行者修改 `references/sources.md` 的模块资料入口，直接链接当前后端 API 的 derive、validate 和 renderController 方法，以及前端 API 的 mount 入口。
2. 计划执行者在 `SKILL.md` 第3.3节加入：

   ```text
   转换 Agent 写模块前，先读取该模块类型的正式函数签名、上下文和返回格式，再转写源逻辑。
   ```

3. 计划执行者从队员可见调用记录统计首次模块检查后的修正次数和耗时，与本轮比较。

### 4.7. 处理免费模型状态格式拒绝

1. 计划执行者用本轮保存的请求和响应定位拒绝字段，分别记录请求格式与角色规则的核对结果；证据未定位的原因列为待验证项。
2. 对 uniqueItems 拒绝，计划执行者另写接口方案：发送给供应商的状态输出 schema 移除 uniqueItems；服务端仍以完整正式 schema 检查重复成员。方案必须说明转换位置、服务端检查路径及重放验收方法，等用户批准后实施。

### 4.8. 保留缺失项恢复和规范化行为

1. 计划执行者在 `references/semantic-experience.md` 的交互规则中加入：

   ```text
   源页面从历史值恢复缺失或无效状态时，转换 Agent 保留恢复条件和保留值的规则，将读取旧消息更新块改为读取原生状态。源页面规范化文本后判断重复时，后端按同一规范化结果保存和校验文本。
   ```

2. 计划执行者复测林茜时，检查转换 Agent 是否按源恢复条件设计 `factsSchema` 和 derive：输入缺少某个选项或该项无效时保留该序号的前值；其余有效项按源顺序合并。
3. 计划执行者提交只有一项变化、缺失项、重复项、无效项和首尾空白的输入，分别核对完整四项结果、后端校验和前端可用状态。

### 4.9. 消除同一状态请求的重复规则

1. 计划执行者修改 `references/semantic-experience.md` 第3章的规则承载判断，写入：

   ```text
   一段规则同时供正文模型与状态 Agent 使用时，转换 Agent 保留世界书条目，由两套预设各自的世界书节点读取。
   ```

2. 计划执行者复测双面恋人时，核对转换产物中e3、e4、e6保留为世界书条目，并且未另复制为 `profile.ruleFiles` 引用的规则文件。
3. 计划执行者调用正式状态dry-run，确认三段规则展开人设宏后各出现一次，保留原文与生效条件。

### 4.10. 修正状态预设追踪诊断

1. 计划执行者另写现有接口修复方案：`preset-parser.ts` 保留导入阶段的未知 marker 诊断；状态提示词组装服务在确认六个状态来源实际展开后，生成本次请求的未解析清单，并据此更新 `assembly` 和 `runtime_trace` 中的诊断。
2. 计划执行者在接口修复方案中列出六个来源全部展开、未知 marker 仍未展开及正文预设不受影响的测试，并要求接口修复执行者逐项对照最终 `messages`、未解析清单和警告。

## 5. 方案待决策项清单

1. 用户需要决定是否批准状态输出 schema 的供应商发送格式调整。
2. 用户需要决定是否为只支持 json_object 的模型增加输出格式策略。

## 6. 计划验收清单

1. 独立审计队员逐行审查修改后的每份文字文档，所有文档的审计结论均为通过。
2. 林茜、人妻、双面恋人均由新的干净上下文队员转换，派发消息仍仅包含 Skill和源文件。
3. 计划执行者完成第4.1至4.6、第4.8及4.9节的逐项验收，保存原文、初值、控制器输出、计算主体、模式判据、重选例外、恢复与规范化及规则注入次数的结果；正式导入及回读通过。
4. 计划执行者记录耗时、调用次数、模块修正次数及剩余失败，完成独立 code-review。
5. 计划执行者交付第4.7节的供应商发送格式方案和第4.10节的状态预设追踪修复方案。

## 7. 非本次目标

1. 本计划不增加包自定义服务端工具、手机会话或原子存档恢复。
2. 本计划不增加 hashing、门禁、并发锁、转换记录校验和依赖安装。

## 8. 已获得的授权

1. 用户已授权 Skill维护、现有确定性工具修复、独立多卡转换、正式验收和 OpenRouter免费模型抽样。
2. 用户已要求保留有效语义原文，禁止临时生成器、hashing及并发锁。
